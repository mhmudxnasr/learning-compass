02 · the operating model

One request, one bounded path, one readback

Hermes is not the database and it is not allowed to improvise the API. It translates an instruction into one focused workflow, uses the first-party client to discover the current contract, sends the request to the Worker, and verifies the canonical record after any write.

Mahmoodstates the outcome
Managerchooses one skill
Site clientdiscovers capability
Workervalidates contract
D1 + R2persist data and files
Receiptproves final state

The manager owns intent and routing. Focused skills own domain rules. The site client owns bounded transport, retries, idempotency, and response shaping. The Worker owns authorization and business invariants. D1 and R2 own durable state. A final answer is grounded only after a canonical readback.

03 · completed hardening

What changed

Manager and skill routing

  • The manager now loads one focused skill before the first API read.
  • “What should I do next?” uses one exact briefing and does not invent projected actions.
  • Activity reporting returns the actual job state without manufacturing a briefing.
  • The operating-system router and site-operator skill were compressed to 7,943 and 11,409 bytes while keeping the decisive rules.
  • Eight unrelated skills were disabled in Hermes configuration, not deleted, to keep the default tool prompt within contract.

Transport and mutation safety

  • Turn IDs propagate across the manager, site client, Worker request, retries, and receipts.
  • Mutation IDs are stable and guarded. A timeout does not authorize a second ambiguous write.
  • The client retries eligible reads, while the manager no longer duplicates that retry policy.
  • Every write follows target read → capability discovery → guarded mutation → canonical readback.
  • Both installed copies of the site client expose the same 52-operation contract and pass parity checks.

Source and feedback correctness

  • Capture preserves an exact verified branch and domain in the same durable transaction.
  • Queue remains a separate commitment. Capturing something does not silently queue it.
  • Recommendation workflows cannot proceed with unresolved candidates or guessed fields.
  • Feedback preserves the user's exact words, uses the supported feedback endpoint, and never invents session IDs.
  • Feedback processing never chains into a fresh recommendation.

Worker and production state

  • Ordinary Learning Compass reads and writes use the public transport contract; the retired token/session gate is absent, while Telegram and provider secrets remain independent.
  • The Hermes API server key was rotated; the new key returns 200 and the old key returns 401.
  • The gateway listens only on 127.0.0.1:8642; the stale alternate port is gone.
  • An exact scan of 13 credential values across 161 changed, injected, and log files found zero matches.
  • Production readiness reports healthy with no blockers, 100% branch coverage, and 257/257 learning events carrying lineage.
  • The verified backup backup_20260826T123709Z passed D1, R2, and restore checks.

05 · practical playbook

How to deal with Hermes

  1. State the outcome. “Capture this and queue it under Systems Thinking” is better than narrating every API step. Hermes should choose the valid path.
  2. Name the target exactly when it matters. Give the source URL, source ID, Thread, lesson, or note ID if you have it. If not, Hermes should perform one bounded lookup.
  3. Keep capture and Queue separate. “Save this” means durable capture. “Commit this to Queue” is a second explicit action. The normal Queue cap is five.
  4. Expect branch verification. Every captured, recommended, or queued item needs a non-pruned branch. If a familiar branch is pruned, Hermes must choose or ask for a valid one; it must not force the old label.
  5. For a write, demand the receipt. The final answer should contain the item ID, resulting state, branch/domain, and the canonical readback used to verify them.
  6. For “what next,” expect one briefing. Hermes should read the exact operational briefing once and act from it. Extra speculative plans are noise.
  7. For jobs, separate acceptance from completion. A 202 response means queued, not done. Ask Hermes to follow the job until the terminal record is verified.
  8. Give feedback in your own words. Hermes should store the raw feedback, structured tags, and disposition without polishing away the meaning. It must not automatically recommend something else.
  9. Use “fix all” for in-scope execution, not invisible permission expansion. Hermes should repair discovered blockers within the named system. It must still stop at destructive, external, or lockout-risk actions.

Good instruction patterns

Capture

“Capture this URL under Systems Thinking. Do not queue it.”

Queue

“Read source rec_…, queue it, then verify it appears in Queue.”

Feedback

“Record this exact feedback on rec_…. Do not recommend anything afterward.”

Job

“Start the supported job and follow it until the final source record proves completion.”

Release

“Run the release checklist, deploy only if every gate passes, then perform live smoke checks.”

Status

“Summarize active agents from their durable reports and live state. Stop stale workers.”

What Hermes must not do

  • Do not guess an endpoint, enum, ID, branch, or request field.
  • Do not repeat a mutation after a timeout until canonical state proves the first attempt did not commit.
  • Do not call a queued job “finished.”
  • Do not treat a rating as permission to create notes or recall cards.
  • Do not create a recommendation because feedback was recorded.
  • Do not deploy because most checks passed. Release gates are conjunctive: all required checks must pass.
  • Do not rotate the active Linux login password unattended when recovery is not proven.

06 · troubleshooting

Read the status code as a routing clue

StatusMeaning in practiceHermes response
400 / 422The request violates the current schema or content boundary.Read the error and capability schema; correct the payload. Do not retry unchanged.
401 / 403The credential is absent, stale, or lacks the required scope.Stop. Verify the configured credential path without printing secrets.
404The target or route is not present in this deployment.Re-read the target and capability list. Never substitute a guessed route.
409A business invariant blocked the write: branch conflict, Queue cap, stale revision, or duplicate role.Read canonical state and resolve the specific conflict. Do not override unless Mahmood explicitly authorizes the relevant exception.
429The bounded client or service is rate-limited.Respect the retry window. Preserve the same turn and mutation identity.
5xx / timeoutThe outcome may be unknown, especially for a write.For reads, use the client's bounded retry. For writes, read canonical state before any second attempt.

Safe operator commands

# Narrow read
site_request.py request GET '/capture/queue' --summary

# Discover the current mutation contract
site_request.py capabilities --domain capture --intent update --method POST --q queue --summary

# Execute a guarded JSON mutation from a reviewed request object
site_request.py mutate request.json --expect-path '/capture/ITEM_ID/record'

# Local release evidence
npm test
npm run build
npm run test:e2e
npm run verify:hermes
git diff --check

# Deploy only after every release gate is green
npx wrangler deploy --config wrangler.toml

Never put an API token or password directly in a shell command, transcript, request file, or final answer. Load it from the configured protected file or secret store.
