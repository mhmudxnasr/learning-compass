# Learning Compass API

Hermes ownership, endpoint permissions, side-effect tiers, routing policy, and specialist receipts are canonical in [`docs/hermes-contract.json`](./hermes-contract.json); this API reference documents the route surface.

## Authentication

Learning Compass API reads and writes do not require an API token or browser session. `POST /auth/session` is retired. Telegram webhooks and optional external providers retain their own dedicated authentication. The local loopback bypass remains only to skip the in-process write rate limiter during development.

## Canonical read models

- `GET /dashboard/briefing` — Momentum source dossier data: active Queue shelf (including each source's Queue rationale and canonical `branch_id`, `branch_label`, and `branch_status`), linked files, weekly completions/notes/recall, evidence-backed insight, recent wins, and actionable attention counts. Legacy streak and next-action fields remain compatible.
- `GET /learning/heatmap`, `GET /learning/detail/:id`, and `/dashboard/briefing` use the canonical activity ledger. Briefing adds `next_action_detail` with the target, reason, and actionable kind while retaining `next_action` compatibility.
- `GET /capture/queue` — five-item active queue read model. Items include optional `context_brief`, a compact source-grounded before-you-start topic breakdown, and the full branch context: `branch` (`{id,label,status,super_category}`), `note` (`{id,title}` when a field note exists), `recall` (`{count,due}`), and `companions` (`{html,pdf}` artifact ids) so the Queue can render branch badges, note links, recall status, and companion buttons without extra round trips. Books and book chapters never appear in Queue; personal reading state remains in Library → Books.
- `GET /recommendations/list` — archive and filtered recommendation records. Use `status=archived` to select completed (`consumed`) and excluded (`rejected`) records before pagination. Use `source=feed` for RSS/Atom captures or `source=manual` to keep feed entries out of the main archive. Every row carries the branch context (`branch_label`, `branch_status`, and `branch.super_category`) plus `note` (`{id,title}`), `recall` (`{count,due}`), and `companions` (`{html,pdf}` artifact ids) so Archive views can render the same badges as the Queue.
- `GET /recommendations/books` — side-effect-free My books records, optionally filtered by `status=active|consumed|rejected`; deleted/non-book rows are excluded. Each book includes Queue-independent `reading_state=saved|reading|finished`, durable `is_primary` reading-desk state, separate `queue_state`, one normalized ordered chapter projection with linked HTML/PDF metadata, `progress`, `next_chapter`, normalized QA/extraction status, `canon_memberships[]`, and every connected `threads[]` membership with its role and expected contribution. The persisted `source_metadata_json.book_reading_state` value is authoritative; legacy recommendation/Queue fields are read-only fallback inputs when it is absent. Verified tree-node branches are linkable; unresolved legacy `recommendations.branch` labels remain visible as `verified:false,linkable:false` with null id/status. The typed `GET /capture/:id/record` uses the same companion projection and never exposes the legacy synthetic Chapter 0. `POST /recommendations/books/:id/reading-state` updates personal reading state and accepts `primary:true` only with `state:"reading"` to atomically pin one reading-desk book without demoting other Reading books; like chapter mutations, it requires a verified non-pruned branch.
- `GET /knowledge/graph` — nodes and evidence-backed edges.
- `GET /knowledge/blind-spots` — unmapped or unconsumed branches.
- `GET /learning/health` — branch health.
- `GET /health/free-tier-budget` — current UTC-day D1 reservation ledger. Dynamic requests stop with `429 daily_free_tier_budget_exhausted` at 4,000,000 estimated rows read or 70,000 estimated rows written, below Cloudflare's free limits.
- `GET /agent/system` — runtime, storage, recovery, and service inventory plus `data_quality`: five named completeness, validity, uniqueness, and lineage contracts with exact affected counts, coverage, and checked time.
- `GET /learning/balance?window=30|90|365` — canonical map-balance read model combining attention share, explicit priority share, coverage, notes, SRS due cards, recall strength, branch depth, and unmapped-source warnings.
- `POST /compass/evaluate` — dry-run server scoring for 3–24 candidates. The response also includes `frontier_shadow`: low-friction, source-grounded candidates with high mechanism match and low known-topic affinity, plus `exploration_shadow`. V2 exposes the winner's deterministic `candidate_set_diversity` and contextual-alignment receipt. Frontier results are shadow-only and never enter Queue or serving.
- `GET /compass/context` — bounded canonical research packet for Hermes before web research: active Thread, actionable missing-material lessons in `recommendation_target_gaps`, typed profile assertions, exclusions, known sources, format fatigue, learning balance, semantic retrieval matches, and the candidate metadata contract. It exposes no scoring authority and creates no recommendation. `POST /compass/semantic/index` explicitly indexes changed recommendations, Threads, Notes, and Units into the private Cloudflare Vectorize corpus; it does not create a recommendation.
- `GET /taste/dna` — vectors, decay, ratings, diversity, and momentum.
- `GET /analytics/heatmaps`, `/analytics/forecast`, `/analytics/taste-drift`, `/analytics/creator-trust`.
- `GET /analytics/hermes` — clean learning-value cohorts, signal population, profile health, self-improvement receipts, queue health, memory, alerts, and engine diagnostics. Compass feedback includes total reactions, neutral deferrals, reason frequency/average score, and lane-level completion, decline, abandonment, deferral, and score summaries. Calibration includes MAE, continuous Brier score, and five reliability buckets comparing predicted versus actual learning value. Administrative exclusions never enter utility metrics.
- `POST /analytics/hermes/recalibrate` — apply a slow, bounded update only after at least 20 training-eligible `learning_value_v2` outcomes; requires `{ "conversation_id": "..." }` and records a receipt. Compass lane adaptation separately requires eight labeled outcomes per lane.
- `GET /analytics/hermes/engine` — return current `shadow|v2` mode and rollout gates. `POST /analytics/hermes/engine/activate` requires all gates plus a conversation ID; `/rollback` returns serving to shadow with a receipt. Generic `PUT /settings/recommendation_engine` cannot change mode and therefore cannot bypass these gates.
- `GET /analytics/hermes/repair` — deterministic dry-run that classifies fabricated score-2 outcomes, administrative exclusions, explicit ratings, and ambiguous records and returns a source-clock snapshot. `POST` applies only with `{ "apply": true, "snapshot_id": "...", "conversation_id": "..." }` matching the current snapshot.
- `GET/POST /analytics/hermes/improvements`, `POST /analytics/hermes/improvements/:id/complete|revert` — open, apply, deploy, fail, close as evidence-backed `no_change`, or roll back conversation-bound improvement receipts. A failed close requires an error; `no_change` requires stored evidence, `after.changed=false`, and `validation.no_change=true`; system/code application requires passed validation and deployment additionally requires a rollback version.
- `GET /analytics/hermes/weekly` — return the last-seven-day clean quality, creator, format, abandonment, and taste-drift report. `POST /analytics/hermes/evaluate` requires `{ "conversation_id": "..." }`, creates only reviewable proposals, and records a no-change/proposal receipt; no cron invokes it.
- `POST /analytics/hermes/backfill` — legacy derived-record compatibility backfill. Defaults to dry-run; applying it requires `{ "dry_run": false, "conversation_id": "..." }` and records a receipt. Historical recommendation/profile correction uses `/analytics/hermes/repair`.
- `GET /capture/:id/record` — canonical source record linking the source, exact feedback and note sections, session history, proposals, artifacts, recall, memory influence, and measured outcome. `feedback` contains the source's parsed Compass events with reason tags, structured fields, disposition, and observational exposure. The response also carries the item's `branch` (`{id,label,status,super_category}`), `companions` (`{html,pdf}` with id/filename/size), and `srs.recall_summary` (`{count,due}`). Book records additionally expose `canon_memberships[]` both on `item` and at the top level. Processing metadata remains available to agents but is not exposed as a user-facing destination.
- `GET /annotations?recommendation_id=...` and `POST /annotations` — source-native evidence ledger. An annotation stores a quote, web/PDF/video/EPUB/artifact locator, context window, language, optional source checksum, and optional Thread/branch ownership; it can be archived without deleting history. `GET /annotations/:id` includes linked Learning Units, notes, and SRS provenance.
- `GET /search/evidence?q=...` — bounded quote/context retrieval that returns durable annotation locators and linked Learning Units. This is the evidence-first retrieval seam for Hermes; broad `GET /search?q=...` remains a navigation search. Broad queries accept 2–200 characters and merge direct typed reads with at most 16 matches from the ordinary `search_idx` substring projection. Literal `%`, `_`, and `\` characters are escaped for that projection. `search_idx` is derived, portable D1 state keyed by `(source,ref_id)` and is rebuilt by maintenance; it is not an FTS virtual table or a second canonical store.
- `GET /feedback/context` — canonical context bundle containing every archived reaction, structured feedback, current profile, and knowledge-map nodes. `feedback_events` preserves every ordinary feedback revision from the append-only learning ledger and every Compass reaction with outcome, reason tags, lane, engine, candidate count, Thread, target lesson, branch, disposition, and exposure instead of collapsing either path into the latest review. Taste Mapper reads this before proposing enhancements.

## Capture and learning

- `GET /learning/core/canon` — read the evergreen Canon atlas, its domain families, curation/field-test counts, verified branch badges, explicit `entry_roles.foundation|representative|boundary` title previews, and optional `q`, `status`, `validation`, or `family` filtering. `GET /learning/core/canon/domains/:id` returns one domain, the three ordered dossiers, consumed/blacklist/source state, and preserved replacement history; `GET /learning/core/canon/entries/:id` is the exact-entry readback.
- `POST /learning/core/canon/domains` and `PATCH /learning/core/canon/domains/:id` — create or edit a family/domain only against a verified non-pruned knowledge branch. A domain cannot become `complete` until all three distinct roles have approved, non-empty dossiers and selection evidence.
- `PUT /learning/core/canon/domains/:id/entries/:role` — create or replace the `foundation`, `representative`, or `boundary` selection. Consumed/blacklisted books are rejected, duplicate selections are blocked, and replacing a title/author requires `replacement_reason`; the prior dossier remains in `canon_entry_revisions`.
- `POST /learning/core/canon/entries/:id/capture` — explicitly deduplicate/capture a selected book as a durable source record and attach the domain branch. Canon rows do not otherwise create recommendations or enter Queue. `POST /learning/core/canon/domains/:id/thread` creates a normal draft Learning Thread only when the domain has a verified non-pruned branch, a complete trio of three distinct approved roles, and at least one selected book already captured; unfinished or empty domains return `409`.
- `GET/POST /learning/core/threads`, `GET/PATCH /learning/core/threads/:id`, `POST /learning/core/threads/:id/status` — create and operate purpose-first Learning Threads with guiding questions, interview context, definitions of done, synthesis, and lifecycle metadata. Learning progression is direct lesson completion only.
- Superseded Threads remain readable at their exact API URL but are omitted from `/learning/core/threads` and `/learning/core/hub`; every mutation returns `learning_thread_superseded` with its replacement object. The retired Three-Book Canon Thread redirects in the client to Learn → Canon rather than being deleted or marked abandoned.
- `DELETE /learning/core/threads/:id` — irreversibly delete one exact Thread and detach its dependent records. Guarded agent use is high-risk: it requires explicit confirmation, an exact live Thread precondition, an idempotency key, and parent-list absence verification. Never use it for ordinary pause or abandonment.
- `GET /learning/core/hub` and `GET /learning/core/threads/:id/path` — read ordered Levels, direct lesson status, optional projects, source branch provenance, and exact Thread/Level/Lesson material ownership. Sources retain coherent companion-pair and truthful NotebookLM state. Artifact and NotebookLM lookups are split into bounded D1 batches so large courses remain readable beyond the per-statement bind limit.
- `POST /learning/core/threads/:id/stages`, `PATCH /learning/core/threads/:id/stages/:stageId`, and `POST /learning/core/threads/:id/stages/:stageId/lessons` — author and update relational Levels and lessons.
- `POST /learning/core/threads/:id/stages/:stageId/start` starts the available Level. `PATCH /learning/core/threads/:id/lessons/:lessonId` records learner-confirmed `not_started|in_progress|completed`; explicitly reopening a completed lesson restores its Level and Thread to active progression. Only lesson completion advances Levels and Threads. Legacy alternate progression routes are unsupported compatibility debt and must not be used by Hermes.
- `POST /learning/core/threads/:id/stages/:stageId/sources` — attach an existing canonical source to a stage by foundation, case, companion, counterevidence, or reference role; it never duplicates the source record. For source-fill work on an existing Thread path, callers must preserve the existing stages/items/order and only research, attach, and verify source coverage.
- `POST /learning/core/threads/:id/lessons/:lessonId/sources` — attach one canonical source to an exact lesson with required `recommendation_id`, `role` (`primary|case|challenge|reference|optional`), and verified non-pruned Level `branch_id`. The atomic write replaces any prior source in the same required role (`primary|case|challenge|reference`) but accumulates distinct `optional` sources, stores the visible role and branch together, and moves a newly pushed `captured` source to `learning_state=attached`; reread the Thread path and source dossier to verify ownership and branch.
- `PATCH /learning/core/threads/:id/projects/:projectId` — update an optional Thread project lifecycle state (`not_started`, `in_progress`, `completed`, or `deferred`). Project state never gates or advances lessons, Levels, or Threads.
- `POST/DELETE /learning/core/threads/:id/sources` — attach reusable sources with primary, supporting, counterevidence, or reference roles without duplicating the canonical source.
- `GET/POST /learning/core/units`, `GET /learning/core/units/:id`, `POST /learning/core/units/:id/relations` — persist and read exact atomic anchored Learning Units and typed `supports`, `contradicts`, `qualifies`, `example_of`, `depends_on`, or `applies_to` relations. New relations require an explanation and endpoint-owned source anchor; reads normalize incoming and outgoing links with canonical branch/domain context.
- `GET /learning/core/contradictions` and `PATCH /learning/core/contradictions/:id` — review anchored Unit contradictions while preserving both claims and sources. Legacy `/brain/contradictions` remains a compatibility-only rating-tension signal.
- `GET /learning/srs/cards/:id` — read one recall card, including cards that are not currently due; missing typed cards return 404.
- `GET /learning/core/weekly` and `GET /learning/core/counterevidence?thread_id=...` — on-demand closure and challenge reads used by Momentum; neither endpoint is scheduled.
- `GET /learning/core/consolidation/:sourceId`, `GET /learning/core/consolidation/open`, `POST /learning/core/consolidation/:id/retry|waive|reconcile` — read and resolve durable cognitive-loop state. Reconcile closes a stranded run only from verified canonical note/Unit/anchor/draft outputs; otherwise it creates or relinks one idempotent `extract_notes` job.
- `GET /learning/core/integrity/health` — report active broken parent relationships and preserved quarantine records.
- `POST /learning/srs/review` — schedule learner-supplied or learner-confirmed Again/Hard/Good/Easy outcomes with reference FSRS-6 (`fsrs-6-ts-fsrs-5.4.1`). Recall scheduling never changes lesson completion.

- `POST /capture`, `GET /capture`, `GET /capture/:id` — universal capture, durable captured-source storage, and enrichment status. New rows use `learning_state:"captured"`. `POST /capture` requires a validated non-pruned top-level `branch_id` (and accepts optional `branch_reason`) so the source and branch are persisted in the same D1 batch; deduplication rejects a conflicting existing branch instead of silently remapping it.
- `GET /capture/personal?item_type=&state=&q=&limit=&offset=` and `GET /capture/personal/:id` — read the typed personal ledger and one exact record. Items expose `book|movie|series|podcast|course|game|album|other`, explicit `planned|in_progress|completed|paused|dropped` state, verified branch, optional release year/duration/progress/unit/rating/tags/note, timestamps, and canonical identity. The list returns exact all-record summaries by type, state, branch, and recent edit month alongside the filtered result count.
- `POST /capture/personal` — create a typed personal record with required `title`, `item_type`, canonical `state`, and verified non-pruned `branch_id`; books also require `creator` as author. Use `state:"completed"` for watched/read/finished media rather than inventing `personal_state`, and use `release_year` rather than `year`. Optional fields are `creator`, `url`, `release_year` (1800 through five years beyond the current UTC year), `duration_minutes`, `progress_current`, `progress_total`, `progress_unit`, numeric `rating` 0–10, `tags`, and `personal_note`. Canonical URL or stable type/title/creator deduplication rejects collisions. The write remains `learning_state=captured`, appends `personal_library_created`, and never enters Queue.
- `PATCH /capture/personal/:id` — edit title, creator, state, branch, URL, `release_year`, duration, progress, unit, rating, tags, or note. Send `null`, `[]`, or an empty string to clear optional values. `item_type` and canonical record ID are immutable; every successful mutation appends `personal_library_updated` and must be verified through the exact GET.
- `POST /assistant/interpret` — interpret a natural-language Egyptian-Arabic or English consumption note into reviewable personal items, high-confidence profile signals, and at most two follow-up questions. This endpoint is read-only with respect to D1; the client must show the extracted items and require explicit user confirmation before calling `POST /capture/personal` or `PUT /brain/profile/assertions/:key`.
- `GET /hardcover` — read the server-side Hardcover mirror, sync status, exact book counts, external status/progress, journal-entry counts, and whether each book is already linked to the Personal Data Studio. This endpoint never exposes the server-only API token.
- `POST /hardcover/sync` — use the configured Worker secret to fetch the authenticated Hardcover library into the D1 mirror. This is an explicit read-only upstream sync; it does not create personal records or Queue items.
- `POST /hardcover/import` — explicitly import unlinked Hardcover books into the typed personal ledger with `{ "branch_id": "verified-branch", "book_ids"?: [123] }`. The branch must be verified and non-pruned; omitting `book_ids` imports all currently unlinked mirror books. Import preserves Hardcover state, progress, rating, author, cover URL, and provenance, and never enters Queue.
- `POST /recommendations/books` — add or update a book with `{ "title", "author", "branch_id", "isbn"?, "url"?, "why_this"? }`. `branch_id` must resolve to a verified non-pruned branch; the write atomically persists canonical branch and domain context and `learning_state=captured`. Duplicate updates preserve an existing explicit personal reading state. Books appear once in Library → Books and never enter Queue.
- `GET/POST /capture/feeds`, `DELETE /capture/feeds/:id` — list, subscribe to, and remove RSS/Atom sources. Subscribe with `{ "url": "https://…", "branch_id": "verified-branch", "limit"?: 1..20 }`; D1 stores the reviewed default branch and newly created source records inherit it atomically with provenance while remaining ordinary captured Library sources. A deduplicated source keeps its prior reviewed mapping, and the import receipt increments `branch_conflicts` instead of silently remapping canonical identity.
- `GET /capture/feeds/:id/entries` — read all imported articles for one feed with pagination.
- `POST /capture/feeds/sync`, `POST /capture/feeds/:id/sync` — check all feeds or one feed now; optional `{ "limit": 1..20 }` caps entries imported per feed. RSS Feeds **Check now** uses 5. Scheduled checks run every six hours without this manual cap.
- `POST /capture/:id/triage` — use `action:"queue"` to promote a branch-mapped captured source, `action:"dequeue"` to neutrally return an active Queue commitment to `captured`, or `action:"exclude"` to administratively exclude it. Queue overflow requires explicit override. Dequeue and exclusion record no negative taste or utility signal.
- `GET /recommendations/export?format=json|md&limit=&offset=` — portable recommendation plus personal-library export. JSON nests typed personal state/progress/tags/note on each canonical row; Markdown emits title, creator, type, personal state, progress, rating, branch, canonical HTTP URL, and personal note. This is a library export, not a complete D1/R2 recovery snapshot.
- `POST /artifacts`, `GET /artifacts`, `GET /artifacts/:id` — generic R2-backed files and metadata. Uploads are limited to inspected HTML, PDF, UTF-8 text/Markdown, and supported audio/video containers; the Worker derives the stored media type from an allow-list plus filename/signature checks instead of trusting multipart metadata. Standalone SVG/XML/XHTML, disguised active content, executable HTML, mismatched extensions, and invalid container signatures are rejected before R2 storage. A staged R2 object is deleted if its D1 insert fails. The generic route also rejects Lite Visual HTML/PDF so its hard gate cannot be bypassed. Readable Arabic HTML remains inline, but it is served in a unique-origin CSP sandbox with `script-src 'none'`, no forms/connections/objects, and only inline styles/data assets. Existing SVG/XML or unknown legacy objects are forced to `application/octet-stream` attachment with `nosniff`; they never render as same-origin active documents. The service worker's dedicated HTML artifact cache is versioned independently so a hardening release evicts responses with older headers. `GET /artifacts` exposes compact validation state, joins the owning source's `notebook_url`, and excludes `scope=book` chapter artifacts from Files. `POST /artifacts` accepts at most one `thread_id`, `stage_id`, or `lesson_id` owner. `GET /artifacts/hub` lists scoped files. NotebookLM cinematic video validation remains unchanged.
- `POST /artifacts/pairs` — the only Visual Lite publication route. Multipart fields are `html`, `pdf`, common `metadata`, and a passing `lite-visual-validation/v5` `validation_receipt` containing a hash-bound `lite-visual-coverage-ledger/v1` claim-traceability check. Metadata requires `pair_id`, `recommendation_id`, full `source_checksum`, `generator=lite-visual`, `workflow_contract=lite-visual-linear/v4`, `asset_policy=code-only`, and `recommended_start=html`. The target may be a non-deleted active or consumed source, so a completed lesson's companion can receive a verified revision. The Worker recomputes file hashes, rejects media, scripts, interaction tags, templates, presets, and remote assets at the boundary, writes both R2 objects, commits both D1 rows plus the exact receipt in one batch, cleans objects after a failed commit, and returns one ready pair. The same already-ready v4 pair plus exact hashes is idempotently reused; a conflicting pair ID returns `409`.
- `POST /capture/:id/visualise` — starts or reads one linear `visualise_source` job. A current ready v4 pair returns `ready`; pending/running work returns `queued`/`working`; a stale completed or failed current-v4 job without a ready pair returns to `retry` from its valid `workflow_step`. A legacy or malformed job is upgraded to the current payload and restarts at `resolve_source`, so obsolete stages can never strand a retry. The declared stages are `resolve_source → extract_source → map_coverage → author_html → render_pdf → validate_pair → publish_pair → verify_record`. The payload declares `extract_source.py`, `lite-visual-source-extraction/v1`, output/manifest names, and exact evidence fields required at every transition. It forbids templates, presets, mind maps, raster/generated images, external image agents, and widgets; books reuse one complete extraction and create one atomic pair per chapter with stable metadata.
- `POST /recommendations/books/:id/chapters/:chapterKey/complete` — mark one generated book chapter finished or unfinished. If registration is absent but an owned matching book HTML/PDF artifact exists, this explicit mutation safely materializes the chapter row first; unknown or unowned keys remain 404. Registration rejects only the retired `key=book`/position `0` placeholder, not a legitimate positive-position chapter whose key is `book`. `GET /recommendations/books` remains side-effect-free and exposes each chapter's HTML/PDF artifact links and completion state.
- `POST /recommendations/books/:id/chapters` — register book chapter metadata and completion state without creating or uploading artifacts; the chapters remain book-scoped and do not appear in Files.
- `GET /artifacts/:id/view` — render Markdown artifacts as a safe, readable HTML document.
- `POST /artifacts/:id/process` — explicitly queue an idempotent `extract_notes` Hermes job; Lite Visual does not call this automatically.
- `POST /recommendations/action` — update recommendation status, rating, review, consumed date, and optionally register an item-specific `notebook_url`, which Learn → Files exposes as the NBLM button.
- `PATCH /recommendations/:id/source-url` — replace the URL opened by **Original source** for one non-deleted source. The route normalizes the URL, rejects dedup conflicts, updates the dedup key, preserves the first previous URL as `source_metadata_json.archive_source_url`, records the new preferred URL, and supports exact source-record verification.
- `PATCH /recommendations/content-types` — atomically correct 1–500 explicitly identified YouTube-backed source records to canonical `content_type:"video"`. Callers must supply the exact allowed prior values in `expected_content_types`; the mutation rejects missing/deleted records, changed preconditions, duplicate IDs, or any non-YouTube URL before writing.
- `DELETE /recommendations/:id/permanent` — permanently remove a non-active source, its feedback/learning history, and linked generated artifacts. This is irreversible; active sources must be archived first.
- `POST /recommendations/map` — attach one or more completed recommendation IDs to an existing map node with `{ "ids": ["..."], "branch_id": "..." }`; rejects missing nodes and incomplete sources, updates outcomes, and returns the verified mapping.
- `GET/POST /sessions`, `POST /sessions/start`, `POST /sessions/:id/return` — server-backed external-handoff lifecycle for original, HTML, PDF, artifact, and NotebookLM targets. Start accepts `thread_id`, `target_kind`, and `target_artifact_id`. Return separates rating from `disposition`; retain/apply creates a durable consolidation run and anchored extraction contract.
- `GET/POST/PUT/DELETE /notes` — source-centric structured notes. `GET /notes` returns the library; `GET /notes/:id` returns one dossier containing the note, same-source reflection/synthesis, note-owned Units, meaningful anchored backlinks, recall state, and progressive distillation. Sections preserve per-block direction; extracted notes pair precise English source blocks with concise Egyptian-Arabic explanation blocks and preserve source-original Arabic quotations. `POST /notes/:id/process` queues explicit processing. `POST /notes` accepts exactly one optional `thread_id`, `stage_id`, or `lesson_id` owner. `DELETE /notes/:id` is irreversible and the guarded agent path requires explicit confirmation, an exact-note precondition, and a post-delete `404` readback before it reports verification.
- `POST /notes/:id/distillation/highlights`, `POST /notes/:id/distillation/syntheses`, and `POST /notes/:id/distillation/highlights/:highlightId/promote` — explicitly retain checksum-bound claims, append user-authored synthesis revisions, and promote a claim to an anchored Unit. Distillation never rewrites canonical note sections; changed blocks remain visibly stale instead of being relocated.
- `GET /brain/resurfacing?limit=5`, `PATCH /brain/resurfacing/:recommendationId/preference`, `POST /brain/resurfacing/presentations`, and `POST /brain/resurfacing/:eventId/action` — read a bounded daily source, explicitly star it, record presentation idempotently per source/Cairo day, and mark it reviewed, snoozed, or dismissed. Selection requires a consumed source with a verified non-pruned branch/domain and never changes Queue, taste, or progression.
- `GET /capture/queue` accepts explicit delivery context and returns advisory fit without reordering Queue. Compass context/evaluation/picks expose explicit delivery context, adaptive depth, and evidence-indexed perspective metadata; unknown values remain neutral.
- `GET /srs/drafts`, `PUT /srs/drafts/:id`, `POST /srs/drafts/:id/approve`, `POST /srs/drafts/:id/reject` — manage existing editable Arabic recall drafts. Automated flash-card generation is disabled, including source-note extraction; new cards require an explicit learner-authored Arabic question and answer through `POST /learning/srs/create`.
- `GET /learning/srs/cards`, `DELETE /learning/srs/cards/:id` — list or permanently remove approved review cards.
- `POST /feedback/record` — the canonical feedback write. Resolve the source with canonical `recommendation_id` (or the exact `source_url`/`title` fallback), preserve the user's words verbatim in required `feedback`, and put any supplied numeric rating in `score` (0–10), not `source_id`, `session_id`, or `rating` aliases. It also accepts `completion_state` (`completed`, `in_progress`, or `stopped`), `disposition` (`undecided`, `retain`, `apply`, `reference`, or `drop`), `branch_id`, `reason_tags`, `expected`, `actual`, `effort`, and `length_minutes`. A supplied branch must exist and be non-pruned; it is persisted atomically even when feedback completes the source. `stopped` requires at least one reason and atomically resolves the source as rejected/excluded so it cannot remain in Queue; `in_progress` alone preserves the Queue commitment. The route preserves the structured record in source metadata, queues Taste Mapper with instructions to read all archived feedback/profile/map context, updates completion when appropriate, returns an explicit analysis/note receipt, and never auto-recommends. A later explicit feedback submission updates the existing consolidation run and canonical disposition rather than leaving the first disposition in place.
- `GET /feedback/proposals` — list pending, applied, blocked, rejected, and reverted changes with policy/deployment receipts.
- `POST /feedback/proposals/:id/apply` — Hermes automatic path. Profile changes require confidence ≥0.8 plus a direct user statement or two evidence items; replacing an explicit user assertion requires a direct contradiction or confidence ≥0.95 with three evidence items. `POST .../approve` is the explicit-user compatibility path, `.../reject` rejects pending work, and `.../revert` restores the typed assertion revision and compatibility projection.
- `GET/POST /agent/memory` — read or write provenance-backed Hermes memories. Durable and hypothesis entries require at least one evidence item; applied feedback proposals also create an approved episodic self-improvement receipt linked to the proposal and update journal.
- Existing `/learning/srs/due`, `/learning/srs/review`, and `/learning/srs/create` remain compatible.

## AI & Curation

- `GET /compass/pick` — return the newest active `ready` or `started` Personal Bayesian Cascade pick, including optional `context_brief`. Multiple concurrent picks may exist; this singular read remains backward-compatible. `GET /compass/pick/:id` returns one exact persisted decision and candidate set and is the canonical guarded-mutation readback.
- `POST /compass/evaluate` — dry-run the same candidate set through legacy and v2 scoring without creating a pick.
- `POST /compass/picks` — submit 3–24 candidates for an open `thread_id` with required `intent`: `solve_problem`, `build_skill`, `deepen_thread`, `discover`, or `queue_fill`. The first three explicitly labeled candidates must cover `fit`, `bridge`, and `challenge`; unlabeled candidates are assigned deterministically. Every candidate needs canonical URL, title, creator, canonicalizable format, branch, expected Thread contribution, one to four source-URL-anchored evidence claims, and an editorial review with `verdict: "recommend"`, substantive `why_worth_time`/`unique_value`, and `depth: "substantive"|"deep"`. A candidate for a missing lesson supplies that gap's exact optional `target_lesson_id`; unknown, completed, populated, or inactive targets are rejected. Candidate and evidence URLs share a public-only verifier that rejects credentials/private targets, validates every redirect, and accepts only verified or access-restricted sources; at most 40 unique URLs are checked per request. Starting a targeted winner atomically attaches it as the lesson's primary material but never changes lesson status. Optional `summary` (≤1,800 chars), 2–8 concise `concepts`, and `mechanism`/`mechanisms` improve deterministic contextual alignment with the Thread; malformed optional context is rejected rather than silently trusted. Books are rejected unless the request includes `allow_books: true`. The Worker checks source verification, entity aliases, semantic duplicates, mastered/blocked rules, Thread contribution, learning balance, typed profile assertions, and clean creator/format outcomes. It stores both v1 and v2 decisions while `recommendation_engine.mode=shadow`, serves v2 only after evidence-gated activation, and labels decision confidence `heuristic_uncalibrated` rather than implying empirical probability calibration. Guarded creation verifies the exact returned `pick_id`, including honest abstentions where no recommendation record exists.
- `POST /compass/pick/:id/candidates` — append research candidates to an abstained pick and rescore the combined set (maximum 24); the replacement pick retains the full decision receipt.
- Compass branch safety is enforced at submission: every candidate must carry a canonical `branch_id` that exists in `tree_nodes`, uses a supported knowledge-map node type, and is not pruned. A confident winner and its `recommendation_meta`/outcome rows retain that exact verified branch ID; missing, unknown, invalid-type, or pruned branches are rejected instead of producing an unlinked recommendation.
- `POST /compass/pick/:id/start` — explicitly move a `ready` pick, or a reachable `abstained` pick as a curator override, into the normal Queue and start its session; the five-item queued/in-progress cap is enforced here.
- `POST /compass/pick/:id/feedback` — record explicit outcome, rating, disposition, reason codes, reflection, `completion_state`, `expected`, `actual`, `effort`, and `length_minutes`. It persists the same `learning_feedback` envelope as `/feedback/record` plus canonical observational exposure (`position=1`, stored candidate count, engine, lane, Thread, target lesson, branch/domain, format, and creator), and returns a visible processing receipt. Exposure is not used as a position-bias correction because Compass exposes one winner. `dismissed`/`not_now` is neutral and returns the source to ordinary captured Library state; `declined`/bad-fit and abandonment are explicit eligibility signals; rating, disposition, and later recall/application outcomes remain independent utility signals. Feedback never auto-recommends.

- `POST /ai/suggest` — legacy compatibility endpoint; new recommendation requests use `/compass/picks`.
- `POST /recommendations/push` — import one or more recommendation records; each item may include optional `context_brief` for the Queue’s before-you-start description.
- `POST /ai/enhance` — copy-edit or sharpen reflection notes.
- `POST /ai/enhance/why` — generate rationale for new recommendation candidates.

## Offline sync and reminders

- Every browser mutation may carry `x-client-mutation-id`; successful responses are cached in `sync_mutations` for safe retries. Deterministic 4xx responses release the reservation, but a redirect or 5xx after handler execution keeps it because the write may have committed. Unknown-outcome reservations are durable safety tombstones and are never removed by ordinary expiry cleanup; reuse returns `409 mutation_outcome_unknown` with `reread_required:true`. The caller must inspect canonical state and may report verified success when the exact desired state exists, but an unresolved or partially committed outcome never becomes replayable merely because time passed.
- `GET /notifications` — browser/Telegram controls and recent delivery history.
- `GET /notifications/vapid`, `POST /notifications/push/subscribe`, `DELETE /notifications/push/:id` — browser reminder registration and status. Remote endpoints must use the default HTTPS origin of a supported browser push vendor (FCM, Mozilla Push, Apple Web Push, or Windows Notification Service), with no credentials, private/local address, or IPv4-mapped IPv6 literal. The fixed vendor-origin policy closes DNS-rebinding ambiguity without a separate DNS time-of-check; delivery never follows redirects. `browser://` remains the non-network in-app subscription form.
- `POST /notifications/telegram` — enable or disable Telegram reminders for a chat ID.
- `POST /notifications/test` — send a test and persist delivered, queued, or failed delivery evidence.

## Agent control protocol v2

- Contract version: `2026-08-26`; protocol: `learning-compass-agent-http/2`.
- `GET /agent/capabilities` — structured allow-list filtered by `domain`, `intent`, `method`, or bounded `q`. The default compact view returns routing/risk metadata only; add `view=full` for schemas, preconditions, idempotency, dry-run, and canonical verification details before mutation.
- `GET /agent/system` — user-visible runtime inventory: storage ownership, the configured six-hour maintenance schedule and responsibilities, on-demand-only workflows, current counts, safety boundaries, active agent contract version, and `data_quality`. That projection declares `scope:"active_sources"`, preserves the all-retained-source inventory as `counts.stored_sources`, and returns five named completeness/validity/uniqueness/lineage checks with exact `affected`, `total`, and `coverage_percent` values.
- `GET /agent/context` — canonical Queue projection, completed Threads, compatibility-only legacy mastered exclusions, branch balance, profile/taste context, and explicit per-section health. Recommendation gaps remain owned by `GET /compass/context`, so `learning_gaps` is `null`, its section is explicitly degraded, and the aggregate returns HTTP `503 unavailable` instead of a plausible healthy empty array. Use the exact Thread path for direct lesson progress. Learning-balance summaries are branch-based and expose no retired synthetic-round projection.
- `GET /agent/openapi.json` — OpenAPI 3.1 generated from the same capability registry, with path parameters, JSON bodies, shared receipt/assertion/error schemas, and operation safety extensions.
- The full capability/OpenAPI body schema for `POST /compass/picks` and its dry-run `POST /compass/evaluate` counterpart mirrors the candidate contract exactly: `intent`, open `thread_id`, and 3–24 candidates are required; each candidate declares the required identity, verified branch, expected contribution, structured evidence, and editorial review fields plus their enum and size bounds. Agents must discover this schema instead of guessing a recommendation payload.
- `POST /agent/request` — dry-run or execute one allow-listed operation with `{method,path,body?,dry_run?,confirm?,idempotency_key?,precondition?,verify?}`. Mutations require `idempotency_key`; high-risk operations additionally require explicit confirmation and an exact-target read precondition with `field` and `equals`. Declared readbacks support batch targets. A failed post-commit readback returns the original successful mutation status with `verified:false`, `mutation_committed:true`, and an explicit verification blocker rather than falsely reporting that the write failed. Successful verification returns the canonical `intent → target → before → mutation_or_job → after → evidence → blocker` receipt.
- `GET /agent/tools` and `POST /agent/tool-call` expose only `list_capabilities` and `site_request`. Legacy direct-write/filter/log tools were removed; product workflows must use canonical routes.
- `GET /agent/briefing` uses one D1 batch and returns one stable next action (`id`, `target`, `reason`, and deep link), exact Queue pressure/cap, and distinct pending/failed/dead-letter/stale/overdue-job, consolidation, branch/domain, direct-lesson-material, proposal, and context-availability blockers. A retry becomes overdue only after 30 minutes when its retry-ledger deadline is absent or due; a future `next_attempt_at` remains a deliberate delay. `GET /agent/activity?limit=` defaults to 10 and caps each section at 25; receipts are recursively redacted/bounded, aggregate health counts remain exact beyond the visible window, and a failed section is marked degraded rather than presented as an empty healthy result. `agent_receipts` persist the verification result after mutations so the activity projection distinguishes committed-but-unverified work from verified work.

Agent mutations reuse product validation and atomically reserve `sync_mutations` keys with method/path/body fingerprints before execution, require a valid `x-api-token` or signed browser session, and audit to `agent_logs`. Concurrent same-key requests cannot both mutate; mismatched reuse returns 409. A possibly committed 5xx keeps the key in an outcome-unknown state until canonical reread, so callers never retry the mutation blindly. Arbitrary SQL, arbitrary paths, and outbound proxying are not exposed. Run `npm run verify:agent-contract` to enforce source/contract/tool/version alignment.

Dynamic responses expose `Server-Timing: app;dur=…`, `X-Response-Time-Ms`, and the conservative `X-D1-Estimated-Rows-Read` / `X-D1-Estimated-Rows-Written` reservation used by the daily free-tier circuit breaker. These are request evidence, not exact D1 query-plan counters; aggregate endpoint percentiles remain in Cloudflare-owned observability and the local benchmark harness.

`GET /brain/profile` includes the compatibility profile plus typed `profile_assertions`, reversible `profile_revisions`, and `profile_health`. Its `taste_vectors` retain the internal `topic` key for scoring and include a readable `label` resolved from the canonical branch map, so profile surfaces never need to display branch IDs. `GET /brain/profile/intelligence` returns only that typed model. `PUT /brain/profile/assertions/:key` creates or replaces any assertion with optimistic `target_version`; `POST /brain/profile/revisions/:id/revert` undoes a revision. `POST /brain/profile` remains the editable compatibility API and mirrors supplied fields into explicit typed assertions.

`GET /brain/branch-deck` returns the personal branch manager projection. `existing` contains only durable top-level `branch` nodes (nested branches and leaves remain topics), while `categories` supplies the live area filters instead of a hardcoded client taxonomy. Each branch includes its readable category, domain, status, priority, linked-source/note/recall counts, latest activity, and editable scope metadata. Archived branches remain readable and reversible.

`POST /brain/branch-explanations` applies reviewed `{ explanations: [{ id, explanation }] }` as metadata-only descriptions to waiting `branch`/`leaf` nodes. It refuses decided branches and never changes status, priorities, taste signals, or lesson completion.

`GET /capture/queue` includes `branch_preflight` for each item. It identifies the mapped branch/domain and flags `conflict: true` when that branch is pruned; queue triage rejects new Queue additions with a `pruned_branch_conflict` response. Every item also carries the enriched `branch` object (`id`, `label`, `status`, `super_category`), `note`, `recall`, and `companions` fields described in the queue contract above. `GET /recommendations/list` rows additionally include `branch_label`, `branch_status`, and `branch.super_category` for branch-aware archive views.

`GET /brain/branches/:id/items` returns the authoritative linked-items ledger for one branch: a `branch` header (label, type, status, domain, priority, and the learning-balance node), the ancestor `path`, `recommendations` (each with rating, consumed date, `recall`, `companions` presence, and `note` link), `notes`, `recall_cards`, pending `srs_drafts`, and R2 `artifacts`. This is the branch dossier the Branch Deck and Map Explorer read; every row is clickable into the unified source dossier.

`POST /capture/:id/branch-map` applies a high-confidence, metadata-only branch mapping to an existing captured, queued, or completed source. It rejects medium/low-confidence mappings and missing or pruned targets; it never changes lesson completion or consumption state. This route is not currently in the generic `/agent/request` allow-list, so Hermes uses the direct endpoint and verifies the source dossier.

`POST /brain/branch-swipe` accepts `keep`, `prune`, `priority`, `hold`, `add`, `update`, or `undo`. Status decisions write the canonical `tree_nodes` state plus one reversible typed `user.profile.branch_preference.*` assertion, a taste signal, and a `recent_signal` refresh; the response includes `profile_sync.synced_at`, `profile_sync.assertion_updated_at`, and a `context_refresh` note. Semantics are explicit and reversible:

- `keep` → `status='love'`, strong positive taste (5.0), `topic_affinity` assertion.
- `prune` → `status='pruned'` + `branch_exploration.is_pruned=1` + priority removed; taste set to a negative signal (0.5/5), assertion category `exclusion` (Compass blocks it). Prune never fabricates a `feedback_proposals` row as "applied" — it is a reversible user exclusion, not a confirmed taste fact.
- `priority` → `status='love'` + one explicit renumbered priority list (this branch becomes rank 1 and the rest shift down, not an unbounded `MAX(rank)+1` tail), `priority` assertion.
- `hold` → `status='held'`, neutral taste (2.5), weak `hypothesis` assertion (confidence 0.6).
- `add` → inserts an `active` exploration branch with `meta_json`; no taste signal until evidence exists. Clients may send `description`, `leaves_sample`, `contrast_hook`, and `parent_id`, stored as branch metadata for future deck reads and agent context.
- `update` → edits the existing branch label, live category, purpose, starter topics, and boundary while preserving status, priority, taste, and profile signals.
- `undo` → reverses the tree row *and* the assertion/taste/priority side effects. When the previous decision was `add`, the branch did not exist before, so `restore_status: "candidate"` removes it entirely.

`POST /brain/branch-suggest` returns review-before-commit new-branch candidates. Input `{ count?: 1..6, mode?: 'surprise'|'expand'|'bridge'|'challenge' }` (default `surprise`/3). The server builds a bounded grounding packet from `loadCompassContext` plus the live branch deck — loved/held/pruned branches, known categories, priority topics, blocked entities, strongest topic affinities, highest-trust creators, recent formats — and asks the LLM (the same `freeAi` wrapper as `/ai/suggest`) for concrete new branch candidates. Each returned item includes a decision brief: `{ id, label, super_category, description, plain_language, leaves_sample, contrast_hook, why_now, evidence_grounding, evidence_confidence, overlap_candidates, suggested_next_move, uncertainty_note, status:'candidate', source:'suggest', mode }`. **Nothing is written**: suggestions never mutate the map or profile; only the user's explicit `add` swipe commits them. If the LLM is unavailable the endpoint succeeds with an empty `suggestions` list and `fallback: true`, and the client offers the grounded copy-prompt instead.

Branch preference is a curation signal only; agents must not infer mastery from it. The agent capability catalog exposes all three branch endpoints so Hermes can inspect and update the map through the same validated path as the UI.
