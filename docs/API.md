# Learning Compass API

Hermes ownership, endpoint permissions, side-effect tiers, routing policy, and specialist receipts are canonical in [`docs/hermes-contract.json`](./hermes-contract.json); this API reference documents the route surface.

## Authentication

Learning Compass API reads and writes do not require an API token or browser session. `POST /auth/session` is retired. Telegram webhooks and optional external providers retain their own dedicated authentication. The local loopback bypass remains only to skip the in-process write rate limiter during development.

## Canonical read models

- `GET /dashboard/briefing` — Home read model: active Queue shelf (including each source's Queue rationale, canonical `branch_id`/`branch_label`/`branch_status`, and newest coherent ready HTML/PDF companion pair), linked Queue files, and one current lesson turn per active Thread. Each visible lesson source also includes its original URL, NotebookLM URL, and selected companion pair so Home can render passive material controls without another request. The response includes weekly completions/notes/recall, evidence-backed insight, recent wins, and actionable attention counts. Legacy streak and next-action fields remain compatible.
- `GET /learning/heatmap`, `GET /learning/detail/:id`, and `/dashboard/briefing` use the canonical activity ledger. Briefing adds `next_action_detail` with the target, reason, and actionable kind while retaining `next_action` compatibility.
- `GET /capture/queue` — five-item active queue read model. Items include optional `context_brief`, a compact source-grounded before-you-start topic breakdown, and the full branch context: `branch` (`{id,label,status,super_category}`), `note` (`{id,title}` when a field note exists), `recall` (`{count,due}`), and `companions` (`{html,pdf}` with artifact id, size, and parsed pair/publication/validation metadata) so the Queue can render branch badges, note links, recall status, passive companion buttons, and a verified offline pack without extra round trips. HTML and PDF are selected only as the newest coherent complete pair; a staged or mismatched pair is never projected as a usable pack. Books and book chapters never appear in Queue; personal reading state remains in Library → Books.
- `GET /recommendations/list` — archive and filtered recommendation records. Use `status=archived` to select completed (`consumed`) and excluded (`rejected`) records before pagination. Use `source=feed` for RSS/Atom captures or `source=manual` to keep feed entries out of the main archive. Every row carries the branch context (`branch_label`, `branch_status`, and `branch.super_category`) plus `note` (`{id,title}`), `recall` (`{count,due}`), and `companions` (`{html,pdf}` artifact ids) so Archive views can render the same badges as the Queue.
- `GET /recommendations/books` — side-effect-free My books records, optionally filtered by `status=active|consumed|rejected`; deleted/non-book rows are excluded. The response carries the editable branch-verified `books[]` projection plus the existing read-only `hardcover` mirror (`state`, `counts`, and `books`). Library → Books composes both without importing: explicit linkage or one unambiguous normalized title/primary-author match displays once with Hardcover's reading status, while unmatched mirror books open Hardcover directly and expose no internal mutations or dossier. Each editable book includes Queue-independent `reading_state=saved|reading|finished`, durable `is_primary` reading-desk state, separate `queue_state`, one normalized ordered chapter projection with linked HTML/PDF metadata, `progress`, `next_chapter`, normalized QA/extraction status, `canon_memberships[]`, and every connected `threads[]` membership with its role and expected contribution. The persisted `source_metadata_json.book_reading_state` value is authoritative when no Hardcover identity is reconciled; legacy recommendation/Queue fields are read-only fallback inputs when it is absent. Verified tree-node branches are linkable; unresolved legacy `recommendations.branch` labels remain visible as `verified:false,linkable:false` with null id/status. The typed `GET /capture/:id/record` uses the same companion projection and never exposes the legacy synthetic Chapter 0. `POST /recommendations/books/:id/reading-state` updates personal reading state and accepts `primary:true` only with `state:"reading"` to atomically pin one reading-desk book without demoting other Reading books; like chapter mutations, it requires a verified non-pruned branch.
- `GET /knowledge/graph` — nodes and evidence-backed edges.
- `GET /knowledge/blind-spots` — unmapped or unconsumed branches.
- `GET /learning/health` — branch health.
- `GET /health/free-tier-budget` — current UTC-day D1 reservation ledger. Dynamic requests stop with `429 daily_free_tier_budget_exhausted` at 4,000,000 estimated rows read or 70,000 estimated rows written, below Cloudflare's free limits.
- `GET /health/ready` — release-contract readiness. In addition to D1/R2/Assets/AI/Vectorize and the Lite Visual signing-key boundary, it verifies the required objects from migrations 0068–0073 and the critical recall-repair, Thread-material, share-intake, and annotation-revision columns. A partially applied new schema therefore fails readiness instead of passing on the older Lite Visual objects alone.
- `GET /agent/system` — runtime, storage, recovery, and service inventory plus `data_quality`: five named completeness, validity, uniqueness, and lineage contracts with exact affected counts, coverage, and checked time.
- `GET /learning/balance?window=30|90|365` — canonical map-balance read model combining attention share, explicit priority share, coverage, notes, SRS due cards, recall strength, branch depth, and unmapped-source warnings.
- `POST /compass/evaluate` — dry-run server scoring for 3–24 candidates. The response also includes `frontier_shadow`: low-friction, source-grounded candidates with high mechanism match and low known-topic affinity, plus `exploration_shadow`. V2 exposes the winner's deterministic `candidate_set_diversity` and contextual-alignment receipt. Frontier results are shadow-only and never enter Queue or serving.
- `GET /compass/context` — bounded canonical research packet for Hermes before web research: active Thread, actionable missing-material lessons in `recommendation_target_gaps`, typed profile assertions, exclusions, known sources, format fatigue, learning balance, semantic retrieval matches, and the candidate metadata contract. It exposes no scoring authority and creates no recommendation. `POST /compass/semantic/index` explicitly indexes changed recommendations, Threads, Notes, and Units into the private Cloudflare Vectorize corpus; it does not create a recommendation.
- `GET /taste/dna` — vectors, decay, ratings, diversity, and momentum.
- `GET /analytics/heatmaps`, `/analytics/forecast`, `/analytics/taste-drift`, `/analytics/creator-trust`.
- `GET /analytics/hermes` — clean learning-value cohorts, signal population, profile health, self-improvement receipts, queue health, memory, alerts, and engine diagnostics. Compass feedback includes total reactions, neutral deferrals, reason frequency/average score, and lane-level completion, decline, abandonment, deferral, and score summaries. Calibration includes MAE, continuous Brier score, and five reliability buckets comparing predicted versus actual learning value. Administrative exclusions never enter utility metrics.
- `POST /analytics/hermes/recalibrate` — apply a slow, bounded update only after at least 20 training-eligible `learning_value_v2` outcomes; requires `{ "conversation_id": "..." }` and records a receipt. Compass lane adaptation separately requires eight labeled outcomes per lane.
- `GET /analytics/hermes/engine` — return current `shadow|v2` mode and rollout gates. `POST /analytics/hermes/engine/activate` requires all gates plus a conversation ID; `/rollback` returns serving to shadow with a receipt. Generic `PUT /settings/recommendation_engine` cannot change mode and therefore cannot bypass these gates.
- `GET /analytics/hermes/repair` — deterministic dry-run that classifies fabricated score-2 outcomes, administrative exclusions, explicit ratings, and ambiguous records and returns a source-clock snapshot. `POST` applies only with `{ "apply": true, "snapshot_id": "...", "conversation_id": "..." }` matching the current snapshot.
- `GET/POST /analytics/hermes/improvements`, `POST /analytics/hermes/improvements/:id/complete|revert` — open, apply, deploy, fail, close as evidence-backed `no_change`, or roll back conversation-bound improvement receipts. A failed close requires an error; `no_change` requires stored evidence, `after.changed=false`, and `validation.no_change=true`; system/code application requires passed validation and deployment additionally requires a rollback version.
- `GET /analytics/hermes/weekly` — return the last-seven-day clean quality, creator, format, abandonment, and taste-drift report. `POST /analytics/hermes/evaluate` requires `{ "conversation_id": "..." }`, creates only reviewable proposals, and records a no-change/proposal receipt; no cron invokes it.
- `POST /analytics/hermes/backfill` — legacy derived-record compatibility backfill. Defaults to dry-run; applying it requires `{ "dry_run": false, "conversation_id": "..." }` and records a receipt. Historical recommendation/profile correction uses `/analytics/hermes/repair`.
- `GET /capture/:id/record` — canonical source record linking the source, exact feedback and note sections, session history, proposals, artifacts, recall, memory influence, and measured outcome. `feedback` contains the source's parsed Compass events with reason tags, structured fields, disposition, and observational exposure. The response also carries the item's `branch` (`{id,label,status,super_category}`), `companions` (`{html,pdf}` with id/filename/size), and `srs.recall_summary` (`{count,due}`). Book records additionally expose `canon_memberships[]` both on `item` and at the top level. Processing metadata remains available to agents but is not exposed as a user-facing destination.
- `GET /annotations?recommendation_id=&thread_id=&branch_id=&status=active|archived&limit=` and `POST /annotations` — source-native evidence ledger. An annotation stores an exact quote of at most 10,000 characters, context windows of at most 2,000 characters each, a serialized selector of at most 12,000 characters, a typed locator, language, checksum, canonical source, required verified non-pruned branch, and optional source-owned Thread. Oversized evidence is rejected rather than truncated. A valid selector URL must resolve, after tracking/fragment normalization, to that exact canonical source or its verified replacement lineage. The guarded insert revalidates current source/branch/domain, Thread, artifact, and URL ownership in the write statement. The Worker computes SHA-256 over the exact stored selector bytes, source id, locator type, quote, and context. Creating the annotation updates the portable search projection but does not create a note, Learning Unit, or recall card.
- `GET /annotations/resolve?source_url=...` — resolve a shared public URL to an existing non-deleted branch-owned source and its preferred active Thread before an anchor is saved. `found:false` means the source must first be captured under a reviewed branch; URL resolution never creates a source implicitly.
- `GET /annotations/:id`, `PATCH /annotations/:id`, and `POST /annotations/:id/archive` — read one annotation with linked Units/notes/recall drafts, revise its quote/context/typed selector within the same non-truncating limits with checksum regeneration, update checksum-neutral language metadata, or archive it without deleting history. A checksum-changing edit creates a new active row with `revision_of_annotation_id`, atomically archives the prior row, and returns `revised:true` plus `previous_annotation_id`; existing derivations therefore keep their exact historical anchor. Both revision and in-place metadata writes require the annotation's stored branch to remain the source's current verified branch and revalidate its exact Thread, artifact, and normalized selector-source ownership. Concurrent or stale-ownership edits fail closed with `409 annotation_revision_conflict`. Editing refreshes Search; archiving removes only the active navigation projection while exact historical reads remain available.
- `POST /api/share-target` — Android/web-share form target. The Worker validates and persists the URL, text, and title before its `303` client redirect; the redirect carries only the opaque intake ID. A URL with no additional prose, or URL-free text, becomes pending `capture`. Any resolved URL plus distinct prose is deliberately pending `review`, because Android does not say whether that prose is a page description or a selected passage; the server never guesses `anchor` from that shape.
- `GET /api/share-intakes/:id` and `GET /api/share-intakes/pending?limit=1..20` — reload one durable share receipt or recover unfinished receipts newest first after the app was closed. `effective_kind` is null until a `review` receipt has been resolved. Exact shared text is limited to 10,000 characters and is rejected rather than truncated; the receipt also persists normalized URL and dedup identity for recovery across fragments, tracking parameters, and verified URL replacements.
- `POST /api/share-intakes/:id/resolve` — persist the explicit completion path for a pending `review` receipt with `{ "kind": "capture" | "anchor" }`. Repeating the same choice is idempotent; a later different choice returns `409 share_intake_resolution_conflict`.
- `POST /api/share-intakes/:id/consume` — close an explicitly classified/resolved capture only with its matching current or historically replaced canonical source, or an anchor only with its exact active annotation. Anchor recovery and consumption require the annotation's normalized selector identity and its exact source's canonical/replacement dedup lineage to match the receipt; an unrelated source with the same quote and raw selector cannot consume it. Target matching, non-deleted source state, annotation/source branch equality, and verified non-pruned branch/domain ownership are predicates of the same guarded update as consumption. An unresolved review returns `409 share_intake_intent_required`; a repeated completion against the same target is idempotent. A pending intake is never a branchless source record: ordinary shares still pass through reviewed branch selection and canonical `/capture` before consumption.
- `GET /search/evidence?q=...` — bounded quote/context retrieval that returns durable annotation locators and linked Learning Units. Both evidence retrieval and broad `GET /search?q=...` return active annotations only while their source is non-deleted and the annotation branch still equals the source's current non-pruned branch under a non-pruned domain; stale index rows are revalidated and maintenance rebuild omits them. Broad Search remains navigation, accepts 2–200 characters, and merges direct typed reads with at most 16 matches from the ordinary `search_idx` substring projection. Literal `%`, `_`, and `\` characters are escaped for that projection. `search_idx` is derived, portable D1 state keyed by `(source,ref_id)` and is rebuilt by maintenance; it is not an FTS virtual table or a second canonical store.
- `GET /feedback/context` — canonical context bundle containing every archived reaction, structured feedback, current profile, and knowledge-map nodes. `feedback_events` preserves every ordinary feedback revision from the append-only learning ledger and every Compass reaction with outcome, reason tags, lane, engine, candidate count, Thread, target lesson, branch, disposition, and exposure instead of collapsing either path into the latest review. Taste Mapper reads this before proposing enhancements.

## Capture and learning

- `GET /learning/core/canon` — read the evergreen Canon atlas, its domain families, curation/field-test counts, verified branch badges, explicit `entry_roles.foundation|representative|boundary` title previews, and optional `q`, `status`, `validation`, or `family` filtering. `GET /learning/core/canon/domains/:id` returns one domain, the three ordered dossiers, consumed/blacklist/source state, and preserved replacement history; `GET /learning/core/canon/entries/:id` is the exact-entry readback.
- `POST /learning/core/canon/domains` and `PATCH /learning/core/canon/domains/:id` — create or edit a family/domain only against a verified non-pruned knowledge branch. A domain cannot become `complete` until all three distinct roles have approved, non-empty dossiers and selection evidence.
- `PUT /learning/core/canon/domains/:id/entries/:role` — create or replace the `foundation`, `representative`, or `boundary` selection. Consumed/blacklisted books are rejected, duplicate selections are blocked, and replacing a title/author requires `replacement_reason`; the prior dossier remains in `canon_entry_revisions`.
- `POST /learning/core/canon/entries/:id/capture` — explicitly deduplicate/capture a selected book as a durable source record and attach the domain branch. Canon rows do not otherwise create recommendations or enter Queue. `POST /learning/core/canon/domains/:id/thread` creates a normal draft Learning Thread only when the domain has a verified non-pruned branch, a complete trio of three distinct approved roles, and at least one selected book already captured; unfinished or empty domains return `409`.
- `GET/POST /learning/core/threads`, `GET/PATCH /learning/core/threads/:id`, `POST /learning/core/threads/:id/status` — create and operate purpose-first Learning Threads with guiding questions, interview context, definitions of done, synthesis, and lifecycle metadata. Learning progression is direct lesson completion only.
- Superseded Threads remain readable at their exact API URL but are omitted from `/learning/core/threads` and `/learning/core/hub`; every mutation returns `learning_thread_superseded` with its replacement object. The retired Three-Book Canon Thread redirects in the client to Learn → Canon rather than being deleted or marked abandoned.
- `DELETE /learning/core/threads/:id` — irreversibly delete one exact Thread and detach its dependent records. Guarded agent use is high-risk: it requires explicit confirmation, an exact live Thread precondition, an idempotency key, and parent-list absence verification. Never use it for ordinary pause or abandonment.
- `GET /learning/core/hub` and `GET /learning/core/threads/:id/path` — read ordered Levels, direct lesson status, optional projects, source branch provenance, source-health projection, and exact Thread/Level/Lesson material ownership. Sources retain coherent companion-pair and truthful NotebookLM state. Artifact and NotebookLM lookups are split into bounded D1 batches so large courses remain readable beyond the per-statement bind limit.
- `POST /learning/core/threads/:id/stages`, `PATCH /learning/core/threads/:id/stages/:stageId`, and `POST /learning/core/threads/:id/stages/:stageId/lessons` — author and update relational Levels and lessons.
- `POST /learning/core/threads/:id/stages/:stageId/start` starts the available Level. `PATCH /learning/core/threads/:id/lessons/:lessonId` records learner-confirmed `not_started|in_progress|completed`; explicitly reopening a completed lesson restores its Level and Thread to active progression. Only lesson completion advances Levels and Threads. Legacy alternate progression routes are unsupported compatibility debt and must not be used by Hermes.
- `GET /learning/core/threads/:id/material-sources?q=&limit=` — Library-first material search for one Thread. It returns active/consumed canonical sources only when their persisted branch and domain exist and are non-pruned, plus source health, coherent companion artifacts, and every current Thread/Level/Lesson placement. `q` searches source title, creator, rationale, branch, and domain; `limit` is 1–50. An exact `recommendation_id` lookup may also supply `expected_source_url`; the source is returned only while its normalized current canonical URL still matches that reviewed URL.
- `POST/PATCH/DELETE /learning/core/threads/:id/stages/:stageId/sources[/:sourceId]` — attach, edit/reorder, or remove one existing canonical source at Level scope. Attach requires a nonblank `expected_contribution`; PATCH also requires the resulting placement to retain a nonblank contribution, including for legacy rows. Public roles are `primary|case|challenge|reference|optional`; non-optional roles are replacement-safe single slots and optional is additive. The mutation persists the contribution, `position`, optional `required`, and canonical branch/domain ownership without duplicating or queuing the source. PATCH/DELETE use an atomic placement-state precondition; stale role, contribution, required flag, order, ownership, or deletion returns `409 source_placement_conflict` without mutating siblings.
- `POST/PATCH/DELETE /learning/core/threads/:id/lessons/:lessonId/sources[/:sourceId]` — attach, edit/reorder, or remove one canonical source at exact Lesson scope with `recommendation_id`, a required nonblank `expected_contribution`, `role` (`primary|case|challenge|reference|optional`), and `position`; PATCH also requires the resulting placement to retain a nonblank contribution, including for legacy rows. Non-optional roles replace the prior same-role placement; optional sources accumulate. A supplied `branch_id` is an exact precondition against the source's persisted verified non-pruned branch. Attaching a reviewed Find material result also supplies `expected_source_url`; a changed normalized canonical URL returns `409 lesson_material_source_changed` and requires review again. A newly attached `captured` source becomes `learning_state=attached`; none of these operations enters Queue, starts a session, or changes progression. PATCH/DELETE use an atomic placement-state precondition, and stale mutations fail with `409 source_placement_conflict` without changing sibling roles or positions.
- `GET/POST /learning/core/threads/:id/lessons/:lessonId/material-request` — read or explicitly create the latest `compass_lesson_material` job for one exact lesson. Creation is allowed only for an incomplete lesson in the current available/in-progress Level when the lesson has neither authored content nor an attached source. Idempotency reuses the same or already-active request. The job payload binds the exact Thread/Level/Lesson, canonical branch/domain context, a Library-first search endpoint, Compass candidate contract, and `attach_policy:explicit_user_action_only`; completion may return one exact ready pick or a reasoned abstention and may never attach, Queue, start, or advance anything. Its Compass pick is stored with `workflow_scope=lesson_material` and the exact `workflow_request_id`, remains outside the normal current-pick/start/feedback lifecycle, and is resolved when the job completes.
- `PATCH /learning/core/threads/:id/projects/:projectId` — update an optional Thread project lifecycle state (`not_started`, `in_progress`, `completed`, or `deferred`). Project state never gates or advances lessons, Levels, or Threads.
- `POST /learning/core/threads/:id/sources`, `PATCH/DELETE /learning/core/threads/:id/sources/:sourceId` — attach, edit/reorder, or remove reusable Thread placements with a required nonblank `expected_contribution` and a primary, supporting, counterevidence, or reference role without duplicating the canonical source. PATCH requires the resulting placement to retain a nonblank contribution; PATCH/DELETE use an atomic role/contribution/order/status and canonical-ownership precondition so a stale mutation returns `409 source_placement_conflict` without compacting siblings.
- `GET/POST /learning/core/units`, `GET /learning/core/units/:id`, `POST /learning/core/units/:id/relations` — persist and read exact atomic anchored Learning Units and typed `supports`, `contradicts`, `qualifies`, `example_of`, `depends_on`, or `applies_to` relations. New relations require an explanation and endpoint-owned source anchor; reads normalize incoming and outgoing links with canonical branch/domain context.
- `GET /learning/core/contradictions` and `PATCH /learning/core/contradictions/:id` — review anchored Unit contradictions while preserving both claims and sources. Legacy `/brain/contradictions` remains a compatibility-only rating-tension signal.
- `GET /learning/srs/cards/:id` — read one recall card, including cards that are not currently due, with active annotation/source-anchor provenance when available. Every card read includes the concurrency token `content_revision`, `scheduler_revision`, `status_revision`, and `repair_status`; missing typed cards return 404.
- `GET /learning/srs/repair` — read up to 200 cards with at least three unacknowledged lapses plus learner-paused cards. Each row includes its transparent reason/threshold, source and anchor provenance, up to 25 review events, up to 25 repair events, and at most three same-Unit/branch/topic comparison candidates. Retired cards do not appear in the queue but remain directly readable.
- `PUT /learning/srs/cards/:id` — explicitly edit learner-authored Arabic question/answer with required `change_kind:"wording"|"semantic"` and the complete latest concurrency token: `expected_content_revision`, `expected_scheduler_revision`, `expected_status_revision`, and `expected_repair_status`. Both increment `content_revision` and atomically append a repair event. `wording` preserves FSRS state and acknowledges existing lapses; `semantic` also increments `scheduler_revision` and resets scheduling to a fresh due card. Existing review events are never deleted.
- `POST /learning/srs/cards/:id/status` and `POST /learning/srs/cards/:id/reset` — both require the complete latest concurrency token. Status changes increment `status_revision`; reset requires `{ "confirm": true }`, increments `scheduler_revision`, and resets scheduling while retaining content and review history. Card and repair-event writes are atomic. A retired card must be restored before editing or resetting. These actions never affect lesson progression.
- `GET /learning/core/weekly` and `GET /learning/core/counterevidence?thread_id=...` — on-demand closure and challenge reads used by Momentum; neither endpoint is scheduled.
- `GET /learning/core/consolidation/:sourceId`, `GET /learning/core/consolidation/open`, `POST /learning/core/consolidation/:id/retry|waive|reconcile` — read and resolve durable cognitive-loop state. Reconcile closes a stranded run only from verified canonical note/Unit/anchor/draft outputs; otherwise it creates or relinks one idempotent `extract_notes` job.
- `GET /learning/core/integrity/health` — report active broken parent relationships and preserved quarantine records.
- `POST /learning/srs/review` — schedule learner-supplied or learner-confirmed Again/Hard/Good/Easy outcomes with reference FSRS-6 (`fsrs-6-ts-fsrs-5.4.1`). Send `card_id`, `grade`, and the complete latest concurrency token (`expected_content_revision`, `expected_scheduler_revision`, `expected_status_revision`, `expected_repair_status`). The schedule update and review event are atomic and increment `scheduler_revision`. Only `repair_status=active` cards may be reviewed. Recall scheduling never changes lesson completion.
- `POST /learning/srs/create` — create one explicit learner-authored Arabic card. Optional `annotation_id` must name an active annotation owned by the same source, branch, and Thread scope; the Worker persists both the annotation ID and a readable `source_anchor`. Needs repair uses this same route for manual split, creating one learner-authored card at a time while leaving the original card unchanged. Automatic generation remains disabled.

- `POST /capture`, `GET /capture`, `GET /capture/:id` — universal capture, durable captured-source storage, and enrichment status. New rows use `learning_state:"captured"`. `POST /capture` requires a validated non-pruned top-level `branch_id` (and accepts optional `branch_reason`) so the source and branch are persisted in the same D1 batch. Both the current dedup identity and every `source_url_replacements.previous_dedup_key`/former URL resolve to the existing canonical source, so re-sharing an old URL cannot create a second record; either match rejects a conflicting existing branch instead of silently remapping it.
- `GET /capture/personal?item_type=&state=&q=&limit=&offset=` and `GET /capture/personal/:id` — read the typed personal ledger and one exact record. Items expose `book|movie|series|podcast|course|game|album|other`, explicit `planned|in_progress|completed|paused|dropped` state, verified branch, optional release year/duration/progress/unit/rating/tags/note, timestamps, and canonical identity. The list returns exact all-record summaries by type, state, branch, and recent edit month alongside the filtered result count.
- `POST /capture/personal` — create a typed personal record with required `title`, `item_type`, canonical `state`, and verified non-pruned `branch_id`; books also require `creator` as author. Use `state:"completed"` for watched/read/finished media rather than inventing `personal_state`, and use `release_year` rather than `year`. Optional fields are `creator`, `url`, `release_year` (1800 through five years beyond the current UTC year), `duration_minutes`, `progress_current`, `progress_total`, `progress_unit`, numeric `rating` 0–10, `tags`, and `personal_note`. Canonical URL or stable type/title/creator deduplication rejects collisions. The write remains `learning_state=captured`, appends `personal_library_created`, and never enters Queue.
- `PATCH /capture/personal/:id` — edit title, creator, state, branch, `release_year`, duration, progress, unit, rating, tags, or note. Send `null`, `[]`, or an empty string to clear optional values. `item_type`, canonical record ID, and canonical URL are immutable on this metadata route; a changed `url` returns `409 source_url_replacement_required` and must use the separately verified `POST/PATCH /recommendations/:id/source-url` flow. Every successful metadata mutation appends `personal_library_updated` and must be verified through the exact GET.
- `POST /assistant/interpret` — interpret a natural-language Egyptian-Arabic or English consumption note into reviewable personal items, high-confidence profile signals, and at most two follow-up questions. This endpoint is read-only with respect to D1; the client must show the extracted items and require explicit user confirmation before calling `POST /capture/personal` or `PUT /brain/profile/assertions/:key`.
- `GET /hardcover` — read the server-side Hardcover mirror, sync status, exact book counts, external status/progress, journal-entry counts, and whether each book is already linked to the Personal Data Studio. This endpoint never exposes the server-only API token.
- `POST /hardcover/sync` — use the configured Worker secret to fetch the authenticated Hardcover library into the D1 mirror. This is an explicit read-only upstream sync; it does not create personal records or Queue items.
- `POST /hardcover/import` — explicitly import unlinked Hardcover books into the typed personal ledger with `{ "branch_id": "verified-branch", "book_ids"?: [123] }`. The branch must be verified and non-pruned; omitting `book_ids` imports all currently unlinked mirror books. Import preserves Hardcover state, progress, rating, author, cover URL, and provenance, and never enters Queue.
- `POST /recommendations/books` — add or update a book with `{ "title", "author", "branch_id", "isbn"?, "url"?, "why_this"? }`. `branch_id` must resolve to a verified non-pruned branch; the write atomically persists canonical branch and domain context and `learning_state=captured`. Duplicate updates preserve the existing canonical URL and explicit personal reading state; supplying a different URL for an existing ISBN returns `409 source_url_replacement_required` so the guarded URL-replacement flow owns verification and lineage. Books appear once in Library → Books and never enter Queue.
- `GET/POST /capture/feeds`, `DELETE /capture/feeds/:id` — list, subscribe to, and remove RSS/Atom sources. Subscribe with `{ "url": "https://…", "branch_id": "verified-branch", "limit"?: 1..20 }`; D1 stores the reviewed default branch and newly created source records inherit it atomically with provenance while remaining ordinary captured Library sources. A deduplicated source keeps its prior reviewed mapping, and the import receipt increments `branch_conflicts` instead of silently remapping canonical identity.
- `GET /capture/feeds/:id/entries` — read all imported articles for one feed with pagination.

Exposure is not used as a position-bias correction because Compass exposes one winner. `dismissed`/`not_now` is neutral and returns the source to ordinary captured Library state; `declined`/bad-fit and abandonment are explicit eligibility signals; rating, disposition, and later recall/application outcomes remain independent utility signals. ## Offline sync and reminders

- Explicit offline packs are a client/service-worker contract rather than a server mutation. Pack scopes are `queue-source|source|book-chapter|book|thread|level`; every pack is same-origin, bounded to 200 resources, versioned from exact URLs/artifact/pair/revision/byte-size identity, and contains one compact revision-hashed snapshot of the already-loaded owner plus complete HTML+PDF groups with one pair ID. Pair builders require both artifacts to declare `publication_state=ready` and `validation_status=passed` and to have positive exact byte sizes. Artifact responses repeat artifact ID, exact byte size, pair ID, role, publication state, and validation state in `X-Learning-Compass-*` headers; the service worker requires every value to match the requested resource and measures the actual response body before it commits the complete new cache and switches the pack index. It reports measured bytes and storage estimates, preserves the previous ready version on stale metadata, byte mismatch, storage exhaustion, or any other failure, marks missing browser-evicted entries `partial`, and supports explicit refresh/remove. Original and NotebookLM URLs are never eligible pack resources, and recall/FSRS endpoints and state are not pack resources.
- Every browser mutation may carry `x-client-mutation-id`; successful responses are cached in `sync_mutations` for safe retries. Deterministic 4xx responses release the reservation, but a redirect or 5xx after handler execution keeps it because the write may have committed. Unknown-outcome reservations are durable safety tombstones and are never removed by ordinary expiry cleanup; reuse returns `409 mutation_outcome_unknown` with `reread_required:true`. The caller must inspect canonical state and may report verified success when the exact desired state exists, but an unresolved or partially committed outcome never becomes replayable merely because time passed.
- `GET /notifications` — browser/Telegram controls and recent delivery history.
- `GET /notifications/vapid`, `POST /notifications/push/subscribe`, `DELETE /notifications/push/:id` — browser reminder registration and status. The fixed vendor-origin policy closes DNS-rebinding ambiguity without a separate DNS time-of-check; delivery never follows redirects. `browser://` remains the non-network in-app subscription form.
- `POST /notifications/telegram` — enable or disable Telegram reminders for a chat ID.
- `POST /notifications/test` — send a test and persist delivered, queued, or failed delivery evidence.

- `GET /agent/briefing` uses one D1 batch and returns one stable next action (`id`, `target`, `reason`, and deep link), exact Queue pressure/cap, and distinct pending/failed/dead-letter/stale/overdue-job, consolidation, branch/domain, direct-lesson-material, proposal, and context-availability blockers. Nonterminal counts include `awaiting_activation` without treating it as claimable, retryable, or lease-expirable. A retry becomes overdue only after 30 minutes when its retry-ledger deadline is absent or due; a future `next_attempt_at` remains a deliberate delay. `GET /agent/activity?limit=` defaults to 10 and caps each section at 25; receipts are recursively redacted/bounded, aggregate health counts remain exact beyond the visible window, and a failed section is marked degraded rather than presented as an empty healthy result. `agent_receipts` persist the verification result after mutations so the activity projection distinguishes committed-but-unverified work from verified work.

Agent mutations are public at the transport layer, reuse product validation, atomically reserve `sync_mutations` keys with method/path/body fingerprints before execution, and audit to `agent_logs`. They do not accept or require a Learning Compass token or browser session. Concurrent same-key requests cannot both mutate; mismatched reuse returns 409. A possibly committed 5xx keeps the key in an outcome-unknown state until canonical reread, so callers never retry the mutation blindly. Arbitrary SQL, arbitrary paths, and outbound proxying are not exposed. Run `npm run verify:agent-contract` to enforce source/contract/tool/version alignment.

Dynamic responses expose `Server-Timing: app;dur=…`, `X-Response-Time-Ms`, and the conservative `X-D1-Estimated-Rows-Read` / `X-D1-Estimated-Rows-Written` reservation used by the daily free-tier circuit breaker. These are request evidence, not exact D1 query-plan counters; aggregate endpoint percentiles remain in Cloudflare-owned observability and the local benchmark harness.

`GET /brain/profile` includes the compatibility profile plus typed `profile_assertions`, reversible `profile_revisions`, and `profile_health`. Its `taste_vectors` retain the internal `topic` key for scoring and include a readable `label` resolved from the canonical branch map, so profile surfaces never need to display branch IDs. `GET /brain/profile/intelligence` returns only that typed model. `PUT /brain/profile/assertions/:key` creates or replaces any assertion with optimistic `target_version`; `POST /brain/profile/revisions/:id/revert` undoes a revision. `POST /brain/profile` remains the editable compatibility API and mirrors supplied fields into explicit typed assertions.

`GET /brain/branch-deck` returns the personal branch manager projection. `existing` contains only durable top-level `branch` nodes (nested branches and leaves remain topics), while `categories` supplies the live area filters instead of a hardcoded client taxonomy. Each branch includes its readable category, domain, status, priority, linked-source/note/recall counts, latest activity, and editable scope metadata. Archived branches remain readable and reversible.

`POST /brain/branch-explanations` applies reviewed `{ explanations: [{ id, explanation }] }` as metadata-only descriptions to waiting `branch`/`leaf` nodes. It refuses decided branches and never changes status, priorities, taste signals, or lesson completion.

`GET /capture/queue` includes `branch_preflight` for each item. It identifies the mapped branch/domain and flags `conflict: true` when that branch is pruned; queue triage rejects new Queue additions with a `pruned_branch_conflict` response. Every item also carries the enriched `branch` object (`id`, `label`, `status`, `super_category`), `note`, `recall`, and `companions` fields described in the queue contract above. `GET /recommendations/list` rows additionally include `branch_label`, `branch_status`, and `branch.super_category` for branch-aware archive views.

`GET /brain/branches/:id/items` returns the authoritative linked-items ledger for one branch: a `branch` header (label, type, status, domain, priority, and the learning-balance node), the ancestor `path`, `recommendations` (each with rating, consumed date, `recall`, `companions` presence, and `note` link), `notes`, `recall_cards`, pending `srs_drafts`, and R2 `artifacts`. This is the branch dossier the Branch Deck and Map Explorer read; every row is clickable into the unified source dossier.

`POST /capture/:id/branch-map` applies a high-confidence, metadata-only branch mapping to an existing captured, queued, or completed source. It rejects medium/low-confidence mappings and missing or pruned targets; it never changes lesson completion or consumption state. This route is not currently in the generic `/agent/request` allow-list, so Hermes uses the direct endpoint and verifies the source dossier.

`POST /brain/branch-swipe` accepts `keep`, `prune`, `priority`, `hold`, `add`, `update`, or `undo`. Status decisions write the canonical `tree_nodes` state plus one reversible typed `user.profile.branch_preference.*` assertion, a taste signal, and a `recent_signal` refresh; the response includes `profile_sync.synced_at`, `profile_sync.assertion_updated_at`, and a `context_refresh` note. Semantics are explicit and reversible:

- `keep` → `status='love'`, strong positive taste (5.0), `topic_affinity` assertion.
- `prune` → `status='pruned'` + `branch_exploration.is_pruned=1` + priority removed; taste set to a negative signal (0.5/5), assertion category `exclusion` (Compass blocks it). Prune never fabricates a `feedback_proposals` row as "applied" — it is a reversible user exclusion, not a confirmed taste fact.
- `priority` → `status='love'` + one explicit renumbered priority list (this branch becomes rank 1 and the rest shift down, not an unbounded `MAX(rank)+1` tail), `priority` assertion.
- `hold` → `status='held'`, neutral taste (2.5), weak `hypothesis` assertion (confidence 0.6).
- `add` → inserts an `active` exploration branch with `meta_json`; no taste signal until evidence exists. Clients may send `description`, `leaves_sample`, `contrast_hook`, and `parent_id`, stored as branch metadata for future deck reads and agent context.
- `update` → edits the existing branch label, live category, purpose, starter topics, and boundary while preserving status, priority, taste, and profile signals.
- `undo` → reverses the tree row _and_ the assertion/taste/priority side effects. When the previous decision was `add`, the branch did not exist before, so `restore_status: "candidate"` removes it entirely.

`POST /brain/branch-suggest` returns review-before-commit new-branch candidates. Input `{ count?: 1..6, mode?: 'surprise'|'expand'|'bridge'|'challenge' }` (default `surprise`/3). The server builds a bounded grounding packet from `loadCompassContext` plus the live branch deck — loved/held/pruned branches, known categories, priority topics, blocked entities, strongest topic affinities, highest-trust creators, recent formats — and asks the LLM (the same `freeAi` wrapper as `/ai/suggest`) for concrete new branch candidates. Each returned item includes a decision brief: `{ id, label, super_category, description, plain_language, leaves_sample, contrast_hook, why_now, evidence_grounding, evidence_confidence, overlap_candidates, suggested_next_move, uncertainty_note, status:'candidate', source:'suggest', mode }`. **Nothing is written**: suggestions never mutate the map or profile; only the user's explicit `add` swipe commits them. If the LLM is unavailable the endpoint succeeds with an empty `suggestions` list and `fallback: true`, and the client offers the grounded copy-prompt instead.

Branch preference is a curation signal only; agents must not infer mastery from it. The agent capability catalog exposes all three branch endpoints so Hermes can inspect and update the map through the same validated path as the UI.

## Settings and organization

- `GET /settings` — stored preferences plus fully resolved defaults, including `profile_automation.mode=manual` (profile changes require explicit review) and `recommendation_engine.mode=shadow`; `PUT /settings/:key` updates one preference group. The appearance group accepts `font`, `custom_font` role stacks (`ui`, `display`, `reading`, `mono`), and bounded `typography` values (`baseSize`, `bodyWeight`, `headingWeight`, `lineHeight`, `letterSpacing`, `displayScale`, `readingMeasure`).

- `GET/PUT /dashboard/layout` — adaptive module pins/order.
