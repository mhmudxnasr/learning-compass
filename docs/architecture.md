# Architecture

## Learning core

D1 keeps canonical Learning Threads, reusable sources, anchored Learning Units, direct lesson status, source outcomes, and derived recommendation signals. `consolidation_runs` plus ordered steps correlate explicit source dispositions with Hermes jobs and expose terminal user state without exposing infrastructure controls. Hermes owns exact-job execution during the active conversation that created or exposed the work. No poller, timer, scheduled consolidation, or scheduled self-improvement exists. Thread and Level progression derives only from direct lesson completion.

Legacy source, note, map, SRS, and REST identifiers remain readable during additive migration. No legacy rating or `mastered` row is silently converted into verified mastery.

Recall uses FSRS-6 through the official `ts-fsrs` package. D1 persists difficulty, stability, lapses, learning steps, scheduled days, state, due date, and scheduler version per card; legacy cards and their review history are migrated without deletion.

The machine-readable Hermes contract in [`docs/hermes-contract.json`](./hermes-contract.json) is canonical for workflow ownership, endpoint permissions, side-effect tiers, and policy routing. This document explains the implementation; it must not redefine those rules.

The Worker owns API routes and explicit durable work. The Vite/Preact client is a static asset bundle served through the Worker’s Assets binding. D1 stores relational state and structured notes; R2 stores large source artifacts. The client uses hash routes so the Worker remains a single-page shell.

Hermes processes only the exact durable work created or exposed by an active conversation. Extraction jobs run `learning-notes-extractor`; feedback analysis runs `taste-mapper`. Every specialist ends with a compact evolution handoff, and `learning-compass-self-evolution` is the single owner that deduplicates evidence and chooses whether to change anything. Profile proposals are typed, versioned, and reversible: Hermes applies a normal change at confidence ≥0.8 with a direct user statement or two evidence items; superseding an explicit user assertion requires a direct contradiction or confidence ≥0.95 with three evidence items. Lower-confidence hypotheses remain pending. Verified narrow skill, prompt, code, test, additive-schema, and workflow improvements may apply after replay and full verification, with Hermes editing directly unless Mahmood explicitly requests an external agent; deployment remains gated by release checks, a rollback version, and live smoke. Validated reversible workarounds may also persist as scoped skill-procedure memory. Broad or insufficiently verified changes remain proposal-only. Evaluated candidates close as applied, deployed, failed/resumable, reverted, or evidence-backed no-change receipts; no candidate creates no D1 churn. There is no scheduled/background self-improvement. Destructive deletion and external publication remain explicit-only. The Worker remains idempotent through job keys, leases, and bounded retries.

Recommendation intelligence uses immutable `learning_events` as the signal ledger and `recommendation_outcomes` as a REST-compatible projection. Administrative exclusion, neutral dismissal, explicit bad fit, rating, learning disposition, completion, and later evidence have separate event types and scopes. `learning_value_v2` combines available rating (25%), explicit retain/apply/reference/drop disposition (25%), and strongest recall/explanation/transfer/application/decision/artifact evidence (50%) without treating missing components as zero. Only explicit utility data enters training cohorts; bad-fit eligibility events can tune fit after the evidence gate, while `not_now` never penalizes a source.

Compass v2 is Thread-first. Each researched set covers fit, bridge, and challenge lanes, requires structured source evidence, canonicalizes format and creator aliases, and scores Thread contribution alongside relevance, source quality, information gain, novelty, format fit, and evidence quality. Shadow mode stores v1 and v2 decisions together. Activation requires 20 global learning-value outcomes, eight in every lane, at least ten shadow decisions, and zero invalid-evidence winners; rollback restores shadow mode. Weight deltas remain bounded to ±0.01 per observation and ±20% of baseline.

Hermes operational state is explicit: typed profile state lives in `profile_assertions` plus append-only `profile_assertion_revisions`; recommendation repair uses a source-clock snapshot and `self_improvement_runs`; `hermes_memory` keeps provenance-backed memories; `agent_job_retries` and `hermes_alerts` keep recovery state. Mutating evaluator, repair, backfill, and recalibration calls require an active conversation identifier and write a receipt. Insights → Hermes reads clean cohorts through `/analytics/hermes`. The weekly evaluator is on-demand compatibility only, never scheduled, and recalibration requires at least 20 training-eligible v2 outcomes.

NotebookLM is a Hermes-controlled grounding service, not a D1 replication target. The Worker exposes a broker heartbeat/recovery protocol at `/notebooklm/health` and `/notebooklm/recover`; it reports `grounded`, `fallback`, or `offline` explicitly and never fabricates corpus statistics or claims to own the local provider session. During explicit feedback on a recommendation, Hermes sends the complete relevant corpus context to the saved Master Corpus notebook, using original source material and Mahmood-authored reflections/feedback. Generated translations, summaries, and Lite Visual companions are excluded as personal thoughts. No background job is created for D1 mutations, and Studio work starts only after an explicit request. For source learning, `/notebooklm/learning/route` requires the exact saved notebook URL and an indexed-source receipt, defaults to one hard source-grounded quiz, permits concept-fit media only, and caps the plan at three outputs. `/notebooklm/learning/receipts` records source `pending|indexed|failed` and artifact `pending|ready|failed` in the existing receipt ledger; ready claims must satisfy the selected output contract and never change lesson, Level, or Thread completion or recall scheduling. Grounded Q&A uses the installed NotebookLM CLI first with the pinned MCP service as fallback; provider truth remains separate from Worker state.

RSS and Atom subscriptions are stored in `feed_sources`; imported GUIDs link to captured Library sources through `feed_entries`. The Worker checks enabled feeds on its six-hour schedule, uses conditional HTTP headers, caps each response at 2 MB and 20 entries, and rejects private/local URLs and unsafe redirect targets.

KOReader reading activity reaches Learning Compass through Hardcover's server-side GraphQL API. `HARDCOVER_API_TOKEN` is a Worker secret; explicit sync mirrors books and reading-journal quotes/notes into `hardcover_books` and `hardcover_journal_entries`, with `hardcover_sync_state` recording observed status. The mirror is intentionally non-canonical. Only an explicit book import with a valid, non-pruned branch creates or updates the canonical recommendation, maps quotes to EPUB source annotations, maps notes to structured reading-journal notes, and exposes the branch/round pill.

The client uses route-level data contracts, IndexedDB for offline mutation queuing, local storage for preferences and session state, and a registered cache-busting service worker. Its Android PWA manifest is the single mobile application contract: standalone launch, adaptive launcher assets, launcher shortcuts, and Android share-to-Library all resolve into the same five-root client. The service worker precaches the fingerprinted application shell plus the bounded Home briefing needed for a first-install offline launch; subsequent bounded read models use network-first cache fallback, while mutation recovery remains owned by IndexedDB. Successful HTML artifact navigations are stored automatically in a separate exact-URL cache and refreshed network-first, so an opened companion remains readable offline without allowing artifact HTML to poison the application-shell cache. PDFs and unopened companions remain network-dependent. Lesson sources expose one material launcher: the stored recommended medium when available, otherwise HTML then Original, with purpose-labelled alternatives and real file/provider state. The Thread path selects a complete HTML/PDF pair by pair ID and revision and batches NotebookLM receipt reduction per source, so the client never mixes companion revisions or calls a mere notebook link “ready.” A Play Store package must be a verified Trusted Web Activity over this origin, not a second WebView codebase. Atlas is a lazy-loaded Cytoscape canvas boundary: it derives clusters from the canonical graph response, starts with major R1 branches, and progressively expands descendants without adding graph code to the base client bundle. `/learning/balance` is the shared read model for Coverage and Hermes: it resolves source activity onto the tree, rolls metrics through tree ancestry, combines attention share with explicit priorities and retention evidence, and keeps unmapped sources visible instead of silently assigning them.

Branches are the primary organizing axis across the product: the Queue, the Branch Deck, the linked-items ledger (`/brain/branches/:id/items`), and the unified source dossier all surface the same branch identity and round. Round derivation lives in `src/services/branch-rounds.ts`: an explicit `R<n>` wins, then legacy `r2-`/`r3-` prefixes. Otherwise R3 requires at least three consumed sources, at least one note, and either three cards or five consumed sources with recall strength at least 0.55; R2 begins with one consumed source, two notes, or three cards; everything else is R1. `recommendations.round` (migration 0035) is a display column for item-level round badges; the canonical branch linkage remains `recommendation_meta.branch_id` with dedup-key prefix resolution as the legacy fallback.

Books is composed as one continuous Learn workspace while keeping two bounded data models. My books reads captured `recommendations` book records and book-scoped chapter/artifact projections; Canon fields use `canon_atlases`, `canon_domains`, `canon_entries`, and `canon_entry_revisions` because an evergreen domain atlas does not share Thread progression or the captured-source lifecycle. Database uniqueness and completion triggers protect the trio invariant. Explicit Canon capture uses the normal captured-source deduplication path, persists the domain branch, and projects `canon_memberships[]` onto the same book identity in list and dossier reads. Manual book intake likewise requires an existing non-pruned branch and atomically persists branch and round. Legacy Shelf/Atlas focus URLs canonicalize to the single Books route.
