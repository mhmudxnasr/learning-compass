# Learning Compass — Project Context

## Purpose

Learning Compass is Mahmood’s private, single-user learning operating system. It turns scattered sources into a disciplined loop:

**define a Learning Thread → capture/curate sources → consume at the original source or a verified canonical companion → reflect → optionally consolidate notes/recall → complete lessons directly → resurface**

The product interface is English-first. Notes Extractor source notes optimize for durable four-year retrieval: precise English source claims and evidence are paired with concise natural Egyptian-Arabic explanation in separate directional blocks. When supported, notes include Misconception vs. Truth and complete Case Studies & Experiments coverage with researchers, year, method, findings, and source-stated limitations. Handwriting remains verbatim in native note blocks without Obsidian syntax; user-authored blocks retain their original register and direction. The product uses the `Africa/Cairo` timezone.

## Product model

- **Personal Assistant** is the natural-language intake layer for consumption history and taste discovery. In Personal Data Studio, the user can describe watched films, read books, finished series, disliked items, or current interests in ordinary Egyptian Arabic or English. `POST /assistant/interpret` returns only a reviewable preview: typed personal items, high-confidence profile signals, and no more than two follow-up questions. The model never writes by itself; explicit user confirmation plus a verified branch is required before the existing personal-library and profile-assertion writes run. This assistant is advisory and does not create Queue items, lessons, recall cards, or recommendations automatically.

- **Hardcover sync/import** is an explicit external-library bridge in Settings → Data & recovery. `POST /hardcover/sync` uses the server-only Worker secret to refresh a D1 mirror of the authenticated Hardcover account; `GET /hardcover` exposes truthful status, progress, covers, journal counts, and import linkage. `POST /hardcover/import` requires a verified non-pruned branch and imports selected or unlinked books into the typed personal ledger while preserving Hardcover provenance and never creating Queue commitments. The token is never returned to the client, and the operator must not guess a branch.

- **Learning Threads** are purpose-first objects for one question, decision, build, or capability. Start the available Level, complete its lessons directly, then continue; the Thread completes when every Level's lessons are complete. A learner-confirmed correction can reopen a completed lesson, which restores its Level and Thread to active progression. Projects, sources, notes, ratings, and recall are optional context and never gate or advance progression. Notes, files, recall cards, and drafts preserve exact Thread, Level, or Lesson ownership. Lesson sources visibly expose their persisted branch. Large course paths batch source-related D1 lookups so hundreds of lessons and attachments remain readable.
- **Books** is the first Library workspace, organized around one explicitly pinned Current Book. The dominant reading desk shows that book’s author, verified branch, Canon and Thread context, progress, one next chapter, available passive HTML/PDF/NotebookLM formats, manual completion, and an accessible chapter disclosure. Below it, My Books is an always-visible, searchable and state-filterable ledger that renders a bounded first page and expands incrementally instead of dumping every saved row. Canon is a visible first-class discovery section with its own search, family filters, and field visualizations that preserve the Foundation, Representative, and Boundary roles. There is no Shelf/Canon tab split, original-book action in the primary flow, or automatic fallback when the current book is cleared, finished, deleted, or tombstoned. One canonical side-effect-free server projection gives the list and focused Book overview identical `is_primary`, personal `saved|reading|finished` state, ordered chapters, normalized companion QA, progress, next chapter, Canon memberships, and connected Threads while omitting synthetic Chapter 0. Canon remains an evergreen relationship model rather than a Thread or second collection. Explicit branch-preserving capture retains one book identity across personal state and Canon membership. Personal book state is independent from Queue commitment; books and chapters never appear in Queue, and Queue alone owns tracked Start/Resume actions.
- **Personal library data** records what Mahmood reads, watches, listens to, studies, or plays without pretending each item is an active learning commitment. One canonical recommendation identity can carry a typed `book|movie|series|podcast|course|game|album|other` record with explicit `planned|in_progress|completed|paused|dropped` state, optional release year/duration/progress/rating/tags/note, a verified branch, and append-only edit lineage. Books share this identity with Library → Books; personal status and progress remain separate from recommendation lifecycle and Queue. Direct ratings are preference evidence, while merely logging or completing media never advances lessons, starts a session, or requests a recommendation.
- **Sources** are reusable inputs. Lesson `primary`, `case`, `challenge`, and `reference` roles are replacement-safe single slots; `optional` is additive so several distinct extensions may coexist. **Learning Units** are atomic claims, concepts, methods, examples, questions, applications, and counterclaims with exact anchors, user synthesis, stance, confidence, and explained typed relations. Meaningful backlinks, cross-branch bridges, and contradiction review derive from those anchored relations, never keyword overlap. Notes are readable projections; Atlas is the navigation taxonomy.
- **Learning progression** is separate from enjoyment and utility. `retain`, `apply`, `reference`, and `drop` are source dispositions; only direct lesson completion advances a Level or Thread.
- **Recall** uses approved, versioned FSRS cards. Automated flash-card and recall-draft generation is disabled, including during retain/apply extraction. New cards require an explicit learner-authored Arabic question and answer, and failed reviews never advance mastery.
- **Consolidation** is explicit and durable, with visible terminal states such as closed, repair required, or waived. Hermes processes the exact work during the active workflow; no learning-core poller or autonomous recommendation chain exists.
- **Progressive note distillation** is explicit and additive. Checksum-bound claims and append-only user synthesis revisions sit above unchanged canonical note sections; explicit promotion creates a note-owned anchored Unit. Changed text marks a claim stale rather than relocating it.
- **Resurfacing** is a passive daily source-review loop with explicit star, reviewed, snooze, and dismiss controls. Frequency decay and seven-day suppression affect only resurfacing order. Frontier states, semantic links, note distillation, and resurfacing never gate or advance lessons.

## Capture and recommendation rules

- Every URL, text, PDF, HTML, video, Telegram, share-target, RSS, and Atom capture becomes a durable `captured` source record. Manual capture and each RSS/Atom subscription require a reviewed non-pruned branch; newly created feed source records inherit that default atomically with mapping provenance, while a deduplicated source preserves its existing reviewed mapping and exposes the conflict in the import receipt. Queue remains the explicit commitment step; enabled feeds refresh every six hours, scheduled imports are capped at 20 deduplicated entries per feed, and manual Check now is capped at five latest entries per feed.
- Global **Add anything** also accepts personal books, movies, series, podcasts, courses, games, albums, and other media. These writes require a verified non-pruned branch, deduplicate canonical URLs or stable type/title/creator identity, remain editable in Settings → Data & recovery, and never enter Queue automatically. A source capture and a personal-media record are distinct intents even though both reuse canonical recommendation identity, ratings, branches, exports, and recovery.
- Queue normally holds five queued/in-progress sources. Explicit triage override is required to exceed the cap. Queue owns start, resume, return, and completion; opening a source, file, or companion elsewhere is passive and never creates a session. Every Queue item carries its branch context (`branch` id/label/status), note presence, recall count/due, and companion artifact links.
- Branches are the primary organizing axis. `tree_nodes` is the branch store; `recommendation_meta.branch_id` is the canonical source-to-branch linkage (dedup-key prefix resolution is the legacy fallback). The taxonomy follows a clean 3-tier domain structure: Super Category (Domain) → Knowledge Branch (`tree_nodes`) → Topics/Leaves (`meta_json.leaves`), with explicit priority rank (1–5) and status (`love`, `active`, `held`, `pruned`). Synthetic round numbering (R1/R2/R3) has been retired. Map → Review → Branches allows creating and editing branch scope, priorities, status, and boundaries. The branch manager, linked-items ledger (`/brain/branches/:id/items`), and unified source dossier present the same canonical branch identity.
- Feedback is explicit, structured, and auditable. The source dossier separates finished, continue-later, and stopped states; stopped feedback requires a reason and atomically exits Queue as rejected/excluded, while not now remains neutral and in-progress feedback preserves the commitment. Rating, disposition, completion, expectation-versus-result, effort, and later recall/application outcomes remain separate. Compass and ordinary feedback share one metadata contract, Taste Mapper receives the complete event history, and every write returns an analysis/note receipt. Processing feedback never requests another recommendation automatically.
- Compass is Thread-first and source-grounded. It exposes current missing-material lessons as exact recommendation targets, verifies every candidate and claim URL through a public-only redirect-safe boundary, and attaches a started targeted pick to that lesson without changing lesson progress. Fit, bridge, and challenge lanes remain bounded by source evidence and rollout gates; decision confidence is explicitly heuristic until a true outcome calibration exists. Mastered/consumed sources and Mahmood’s standing exclusions are always applied.
- Adaptive depth uses direct lesson completion and explicit depth feedback only as advisory ranking signals. Perspective labels require candidate evidence indexes, and explicit delivery context may describe device, time, energy, language, or reading mode; unknown values stay neutral and Queue order remains canonical.
- User-authored reflection is never rewritten. Invisible AI may enrich, rank, classify, and explain. Typed profile changes have provenance, confidence, version history, and reversible undo; Hermes self-evolution is evidence-gated, explicit, and unscheduled.

## Frontend contract

The shipped client is the **Botanical Folio / Evidence Ledger**: a green-and-cream studio with five root destinations and 12 grouped modes, with subordinate focus filters:

| Root destination | Grouped modes and subordinate focuses |
|---|---|
| Home | Today |
| Library | Books (Reading desk, My books, integrated Canon fields), Triage (Queue, Feeds), Archive, Files |
| Learn | Practice (Notes by default, Recall), Threads (legacy Paths aliases) |
| Map | Atlas, Review (one Branch Dossier combining status, priority, scope, coverage, retention, and attention) |
| Settings | Personal (Learning profile, Preferences), Data & recovery (editable personal Data Studio plus explicit completeness, validity, uniqueness, lineage, export, and recovery contracts), System |

Desktop uses a persistent root rail, main canvas, and optional contextual inspector; there is no permanent context pane. Search, Add anything, and sync state are global rail tools rather than extra destinations. Add anything begins with a compact type choice and four required core decisions, with progress, rating, tags, and notes behind disclosure. Mobile and tablet replace the rail with a five-item bottom dock plus separate Search and Capture utilities; primary modes remain an equal-width visible grid and subordinate filters remain compact wrapping controls. Selected-object inspection becomes a sheet or pushed detail view. Typed Thread and Level routes remove the global Learn switcher, return through one Threads breadcrumb, and use the task-language sections Now, Lessons, Projects, and Resources. Normal Level links and Lesson Level breadcrumbs target the exact `tab=curriculum&level=<id>` state instead of leaving the Thread command center; typed Level routes remain deep-link recovery surfaces. Lesson routes omit progression/contract/guide panels, lead with an action bar only when a real navigation or progression action exists, render one truthful readiness state, reduce HTML/PDF/Original/NotebookLM access to compact accessible icons, and bound secondary sources behind More materials. Typed object routes preserve Source, Thread, Note, Unit, Recall Card, Branch, Node, Collection, Book, and Artifact identity. Legacy hashes canonicalize to purposeful routes and unknown hashes render recovery.

Atlas fills all workspace height remaining below the Map mode switcher. It keeps selection distinct from expansion: one tap selects and centers a node, while a repeated or double tap progressively reveals its next connected layer. Typed node routes reveal and focus the exact node without remounting the workspace. Search reveals canonical ancestry and resolves conflicting filters; domain and frontier filters always reflect the actual canvas and expose direct recovery when no nodes match. A selected node can isolate its canonical ancestry, subtree, and immediate semantic neighbors, while arrow-key traversal and Enter provide a direct keyboard path through visible nodes. The graph renders before the advisory frontier projection finishes, preference saves expose their state and cannot overwrite Reset, reduced motion removes hover pulsing, and large constellations use bounded local force interactions instead of all-pairs work.

Display preferences are functional system settings, not previews. Preferences prioritize complete workspace styles, plain-language comfort controls, and learning behavior; expert theme, font, typography, custom-system, and Map tuning remain available through native progressive disclosure. Theme and custom palette choices update every semantic color plane and appropriate foreground, typography updates the application font contract, density changes shared spacing and control dimensions, corner style changes shared panel/control geometry, and reduced motion disables transitions throughout the product. These choices persist across reloads, while a server-saved custom palette remains authoritative when the custom theme is hydrated.

Android uses the same canonical client as an installable PWA rather than a separate product fork. The manifest supplies 192px, 512px, and maskable launcher assets, standalone launch, Capture/Queue/Recall shortcuts, and the existing share-to-Library target. The registered service worker precaches the complete fingerprinted shell plus the bounded Home briefing required for a first-install offline launch. It also caches each HTML reading companion under its exact artifact URL after the first successful online open, refreshes that copy on later online opens, and falls back to it offline without changing the interface; artifact navigations never overwrite the application shell. Installed mode respects Android safe areas and removes browser overscroll, and a dismissible install card appears only when Android reports that installation is available. A future Play Store release wraps this PWA as a Trusted Web Activity with Digital Asset Links; a generic WebView wrapper is not an accepted architecture.

`client/src/main.tsx` is cut over to `client/src/app/entry.tsx`. The replacement is composed under `client/src/app`, `client/src/shell`, `client/src/workspaces`, and shared components; the retired monolithic shell/registry/styles files are removed as part of the cutover.

## System architecture and ownership

- `src/` contains the Hono Cloudflare Worker, API routes, domain logic, and scheduled infrastructure.
- `client/` contains the Vite + Preact + TypeScript application.
- `schema.sql` is the base schema; `migrations/` are ordered, idempotent production migrations.
- D1 is canonical for product records, typed personal-library state, learning state, graph data, receipts, and profile assertions. R2 stores large artifacts and linked reading companions. Obsidian archive/export applies only to extracted non-book notes; books and book chapters remain in Learning Compass.
- API mutations retain stable client IDs, offline outbox/retry/discard behavior, conflict visibility, and successful-response receipts. REST compatibility remains intact. `/agent/system.data_quality` reports named source-identity, branch, uniqueness, event-lineage, and feed-default contracts instead of an opaque quality score. Source annotations preserve quote/context, durable locators, language, checksums, and downstream provenance; `/search/evidence` returns that evidence ledger for Hermes instead of asking an agent to cite free-form summaries.
- Heavy graph code stays lazy-loaded. The base client target is at or below 150 KB gzip excluding lazy graph/vendor chunks.

## Hermes and reading companions

Lite Visual `lite-visual-validation/v6` receipts are HMAC-attested. A corpus replacement is bound to one exact ordered target set, manifest, aggregate `lite-visual-corpus-audit/v1`, source set, active durable job set, immutable workflow runs, and current-pair supersession state. The Worker requires R2, verifies both stored objects, enforces unique pair roles, keeps all replacement pairs hidden during bounded multi-day staging, and uses one guarded D1 transaction to expose the complete corpus and complete its exact jobs. Any failure before activation leaves the prior corpus fully visible. Production mutation remains prohibited until every immutable target has accepted signed semantic-completeness evidence and independent review; the authoritative target-set SHA-256 is `18a24b536b45d5c95fd55e638b334f8f933d6707ee024c6672f3fcc45b451f3f` and must not be narrowed to make validation pass.

Lite Visual creates one atomic Arabic HTML+PDF pair for normal sources and one pair per book chapter. The semantic HTML article is the single canonical reading body and the A4 PDF is printed from that exact file. One source router acquires the body: a hash-verified cache, the accepted hash-bound Riyadh transcript receipt, Mozilla Readability plus bounded Playwright fallback, YouTube API/yt-dlp captions, no-caption-only audio transcription, PyMuPDF plus Tesseract OCR, EPUB spine extraction, Pandoc, or direct UTF-8. The `riyadh-salihin-local-transcript/v1` lane verifies the untouched transcript hash, official audio hash, receipt/chunk quality, monotonic segments, canonical media identity, and every repeated-passage family before any explicit timestamp-label cleanup. For YouTube, audio transcription is permitted only after a complete caption inventory positively confirms zero manual and zero generated tracks; lookup failures and unusable published tracks block audio. Its `lite-visual-source-extraction/v1` receipt must be complete before gapless coverage begins. After reading Intent and Frontend Design, Hermes designs every artifact fresh from its source; templates, style locks, reusable palettes, preset themes/layouts, mind maps, raster/generated images, external image agents, scripts, widgets, and mandatory pauses are forbidden. Prose carries argument and nuance; native structures and rare source-grounded inline SVG are the only code-native aids. Every normalized source word belongs to a reviewed semantic span of at most 120 words; every span has exactly one matching claim and a real authored anchor outside the appendix. The standard path idempotently embeds one visible complete-source edition whose scope wrappers preserve every normalized accepted source word once and in order; summaries orient but never substitute. Exact checkpoint evidence, deterministic RTL/accessibility/responsive/200%-text/print-text/A4/all-page/source-parity checks, an HMAC-attested v6 receipt, a fresh signed aggregate audit, exact manifest/source/immutable-run/job/current-pair binding, request-owned R2 objects, guarded ready-pair revision, atomic corpus activation, canonical-state recovery, and source-record verification are mandatory. Raw sources remain separate, hard technical material defaults to beginner teaching unless competence is explicit, and Notes Extractor never starts automatically.

Hermes remains the procedural Learning Compass operating system. Agent control protocol v2 (`2026-08-26`) exposes one structured capability registry that drives filtered discovery and OpenAPI, bounded Queue/profile/health context, and only two generic Worker tools (`list_capabilities`, `site_request`). Hermes uses the first-party `learning-compass-site-operator/scripts/site_request.py` client over the live Worker API instead of an MCP bridge, so Learning Compass adds no permanent model-tool schema or subprocess server. It reads the narrowest endpoint required, uses `GET /agent/briefing` only for open-ended manager/next-action requests, and loads `/agent/context` only when a decision depends on broader live state. Recommendation target gaps come from `/compass/context`; direct lesson progress comes from the Thread path. `GET /agent/activity` exposes verified receipts, jobs, and pending proposals. Settings → System presents one operational-health ledger for jobs, recall load, context health, calibration, and rollout readiness. Agent mutations retain request-fingerprinted idempotency, exact-target high-risk preconditions, canonical readback, and receipts; a timeout, handler 5xx, or committed-but-unverified receipt forces one canonical reread before any retry. SOUL owns stable manager behavior, USER stable preferences, MEMORY stable environment facts, skills procedures, typed D1 assertions provenance-backed preferences, and live Worker reads all current state. D1 memory keeps one active/approved value per key, replaces value plus evidence atomically, and emits Unicode-aware retrieval receipts that account for selected and excluded memories/assertions. Prompt, tool, memory-tail, duplicate-entry, active-skill, and profile-parity budgets are deterministic release gates. NotebookLM uses its local CLI only. Hermes owns recommendation research, feedback handling, typed profile learning, memory provenance, code-only Lite Visual, RSS, site operations, and self-evolution, with no scheduled autonomous poller. Internal prompts, job controls, and secrets never render in normal product surfaces.

Capture interoperability includes a least-privilege Manifest V3 browser extension that opens the normal global capture dialog with a page URL or selected passage; every capture becomes a `captured` Library record. Learning Compass ordinary reads and writes require no API token or browser unlock session, and `POST /auth/session` is retired. Telegram intake remains separately protected by its webhook secret, optional allowed chat ID, and durable `update_id` deduplication. Recovery is explicit and portable: migrations `0066` and `0067` are already applied and must not be replayed; `0068_lite_visual_corpus_activation.sql` must be the sole pending migration before release. The pre-migration gate requires a complete checksummed D1-plus-R2 snapshot, disposable restore rehearsal, D1 Time Travel bookmark, and captured Worker version as documented in `docs/recovery.md`.
