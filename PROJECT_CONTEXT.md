# Learning Compass — Project Context

## Purpose

Learning Compass is Mahmood’s private, single-user learning operating system. It turns scattered sources into a disciplined loop:

**define a Learning Thread → capture/curate sources → consume at the original source or a verified canonical companion → reflect → optionally consolidate notes/recall → complete lessons directly → resurface**

The product interface is English-first. Notes Extractor source notes optimize for durable four-year retrieval: precise English source claims and evidence are paired with concise natural Egyptian-Arabic explanation in separate directional blocks. When supported, notes include Misconception vs. Truth and complete Case Studies & Experiments coverage with researchers, year, method, findings, and source-stated limitations. Handwriting remains verbatim in native note blocks without Obsidian syntax; user-authored blocks retain their original register and direction. The product uses the `Africa/Cairo` timezone.

## Product model

- **Learning Threads** are purpose-first objects for one question, decision, build, or capability. Start the available Level, complete its lessons directly, then continue; the Thread completes when every Level's lessons are complete. Projects, sources, notes, ratings, and recall are optional context and never gate or advance progression. Notes, files, recall cards, and drafts preserve exact Thread, Level, or Lesson ownership. Lesson sources visibly expose their persisted branch. Large course paths batch source-related D1 lookups so hundreds of lessons and attachments remain readable.
- **Books** is the first Library workspace, organized around one explicitly pinned Current Book. The dominant reading desk shows that book’s author, verified branch, Canon and Thread context, progress, one next chapter, available passive HTML/PDF/NotebookLM formats, manual completion, and an accessible chapter disclosure. Below it, My Books is an always-visible, searchable and state-filterable ledger that renders a bounded first page and expands incrementally instead of dumping every saved row. Canon is a visible first-class discovery section with its own search, family filters, and field visualizations that preserve the Foundation, Representative, and Boundary roles. There is no Shelf/Canon tab split, original-book action in the primary flow, or automatic fallback when the current book is cleared, finished, deleted, or tombstoned. One canonical side-effect-free server projection gives the list and focused Book overview identical `is_primary`, personal `saved|reading|finished` state, ordered chapters, normalized companion QA, progress, next chapter, Canon memberships, and connected Threads while omitting synthetic Chapter 0. Canon remains an evergreen relationship model rather than a Thread or second collection. Explicit branch-preserving capture retains one book identity across personal state and Canon membership. Personal book state is independent from Queue commitment; books and chapters never appear in Queue, and Queue alone owns tracked Start/Resume actions.
- **Sources** are reusable inputs. Lesson `primary`, `case`, `challenge`, and `reference` roles are replacement-safe single slots; `optional` is additive so several distinct extensions may coexist. **Learning Units** are atomic claims, concepts, methods, examples, questions, applications, and counterclaims with exact anchors, user synthesis, stance, confidence, and explained typed relations. Meaningful backlinks, cross-branch bridges, and contradiction review derive from those anchored relations, never keyword overlap. Notes are readable projections; Atlas is the navigation taxonomy.
- **Learning progression** is separate from enjoyment and utility. `retain`, `apply`, `reference`, and `drop` are source dispositions; only direct lesson completion advances a Level or Thread.
- **Recall** uses approved, versioned FSRS cards. Automated flash-card and recall-draft generation is disabled, including during retain/apply extraction. New cards require an explicit learner-authored Arabic question and answer, and failed reviews never advance mastery.
- **Consolidation** is explicit and durable, with visible terminal states such as closed, repair required, or waived. Hermes processes the exact work during the active workflow; no learning-core poller or autonomous recommendation chain exists.
- **Progressive note distillation** is explicit and additive. Checksum-bound claims and append-only user synthesis revisions sit above unchanged canonical note sections; explicit promotion creates a note-owned anchored Unit. Changed text marks a claim stale rather than relocating it.
- **Resurfacing** is a passive daily source-review loop with explicit star, reviewed, snooze, and dismiss controls. Frequency decay and seven-day suppression affect only resurfacing order. Frontier states, semantic links, note distillation, and resurfacing never gate or advance lessons.

## Capture and recommendation rules

- Every URL, text, PDF, HTML, video, Telegram, share-target, RSS, and Atom capture becomes a durable `captured` source record. Queue remains the explicit commitment step; enabled feeds refresh every six hours, scheduled imports are capped at 20 deduplicated entries per feed, and manual Check now is capped at five latest entries per feed.
- Queue normally holds five queued/in-progress sources. Explicit triage override is required to exceed the cap. Queue owns start, resume, return, and completion; opening a source, file, or companion elsewhere is passive and never creates a session. Every Queue item carries its branch context (`branch` id/label/status), note presence, recall count/due, and companion artifact links.
- Branches are the primary organizing axis. `tree_nodes` is the branch store; `recommendation_meta.branch_id` is the canonical source-to-branch linkage (dedup-key prefix resolution is the legacy fallback). The taxonomy follows a clean 3-tier domain structure: Super Category (Domain) → Knowledge Branch (`tree_nodes`) → Topics/Leaves (`meta_json.leaves`), with explicit priority rank (1–5) and status (`love`, `active`, `held`, `pruned`). Synthetic round numbering (R1/R2/R3) has been retired. Map → Review → Branches allows creating and editing branch scope, priorities, status, and boundaries. The branch manager, linked-items ledger (`/brain/branches/:id/items`), and unified source dossier present the same canonical branch identity.
- Feedback is explicit, structured, and auditable. The source dossier separates finished, continue-later, and stopped states; stopped feedback requires a reason, while not now remains neutral. Rating, disposition, completion, expectation-versus-result, effort, and later recall/application outcomes remain separate. Compass and ordinary feedback share one metadata contract, Taste Mapper receives the complete event history, and every write returns an analysis/note receipt. Processing feedback never requests another recommendation automatically.
- Compass is Thread-first and source-grounded. It exposes current missing-material lessons as exact recommendation targets, verifies every candidate and claim URL through a public-only redirect-safe boundary, and attaches a started targeted pick to that lesson without changing lesson progress. Fit, bridge, and challenge lanes remain bounded by source evidence and rollout gates; decision confidence is explicitly heuristic until a true outcome calibration exists. Mastered/consumed sources and Mahmood’s standing exclusions are always applied.
- Adaptive depth uses direct lesson completion and explicit depth feedback only as advisory ranking signals. Perspective labels require candidate evidence indexes, and explicit delivery context may describe device, time, energy, language, or reading mode; unknown values stay neutral and Queue order remains canonical.
- User-authored reflection is never rewritten. Invisible AI may enrich, rank, classify, and explain. Typed profile changes have provenance, confidence, version history, and reversible undo; Hermes self-evolution is evidence-gated, explicit, and unscheduled.

## Frontend contract

The shipped client is the **Botanical Folio / Evidence Ledger**: a green-and-cream studio with five root destinations and 12 grouped modes, with subordinate focus filters:

| Root destination | Grouped modes and subordinate focuses |
|---|---|
| Home | Today |
| Library | Books (Reading desk, My books, integrated Canon fields), Triage (Queue, Feeds), Archive, Files |
| Learn | Threads (legacy Paths aliases), Practice (Notes, Recall) |
| Map | Atlas, Review (one Branch Dossier combining status, priority, scope, coverage, retention, and attention) |
| Settings | Personal (Learning profile, Preferences), Data & recovery, System |

Desktop uses a persistent root rail, main canvas, and optional contextual inspector; there is no permanent context pane. Search, Capture to Library, and sync state are global rail tools rather than extra destinations. Mobile and tablet replace the rail with a five-item bottom dock plus separate Search and Capture utilities; primary modes remain an equal-width visible grid and subordinate filters remain compact wrapping controls. Selected-object inspection becomes a sheet or pushed detail view. Typed object routes preserve Source, Thread, Note, Unit, Recall Card, Branch, Node, Collection, Book, and Artifact identity. Legacy hashes canonicalize to purposeful routes and unknown hashes render recovery.

Atlas fills all workspace height remaining below the Map mode switcher. It keeps selection distinct from expansion: one tap selects and centers a node, while a repeated or double tap progressively reveals its next connected layer. Typed node routes reveal and focus the exact node without remounting the workspace. Search reveals canonical ancestry and resolves conflicting filters; domain and frontier filters always reflect the actual canvas and expose direct recovery when no nodes match. A selected node can isolate its canonical ancestry, subtree, and immediate semantic neighbors, while arrow-key traversal and Enter provide a direct keyboard path through visible nodes. The graph renders before the advisory frontier projection finishes, preference saves expose their state and cannot overwrite Reset, reduced motion removes hover pulsing, and large constellations use bounded local force interactions instead of all-pairs work.

Display preferences are functional system settings, not previews. Preferences prioritize complete workspace styles, plain-language comfort controls, and learning behavior; expert theme, font, typography, custom-system, and Map tuning remain available through native progressive disclosure. Theme and custom palette choices update every semantic color plane and appropriate foreground, typography updates the application font contract, density changes shared spacing and control dimensions, corner style changes shared panel/control geometry, and reduced motion disables transitions throughout the product. These choices persist across reloads, while a server-saved custom palette remains authoritative when the custom theme is hydrated.

Android uses the same canonical client as an installable PWA rather than a separate product fork. The manifest supplies 192px, 512px, and maskable launcher assets, standalone launch, Capture/Queue/Recall shortcuts, and the existing share-to-Library target. The registered service worker precaches the complete fingerprinted shell plus the bounded Home briefing required for a first-install offline launch. It also caches each HTML reading companion under its exact artifact URL after the first successful online open, refreshes that copy on later online opens, and falls back to it offline without changing the interface; artifact navigations never overwrite the application shell. Installed mode respects Android safe areas and removes browser overscroll, and a dismissible install card appears only when Android reports that installation is available. A future Play Store release wraps this PWA as a Trusted Web Activity with Digital Asset Links; a generic WebView wrapper is not an accepted architecture.

`client/src/main.tsx` is cut over to `client/src/app/entry.tsx`. The replacement is composed under `client/src/app`, `client/src/shell`, `client/src/workspaces`, and shared components; the retired monolithic shell/registry/styles files are removed as part of the cutover.

## System architecture and ownership

- `src/` contains the Hono Cloudflare Worker, API routes, domain logic, and scheduled infrastructure.
- `client/` contains the Vite + Preact + TypeScript application.
- `schema.sql` is the base schema; `migrations/` are ordered, idempotent production migrations.
- D1 is canonical for product records, learning state, graph data, receipts, and profile assertions. R2 stores large artifacts and linked reading companions. Obsidian archive/export applies only to extracted non-book notes; books and book chapters remain in Learning Compass.
- API mutations retain stable client IDs, offline outbox/retry/discard behavior, conflict visibility, and successful-response receipts. REST compatibility remains intact. Source annotations preserve quote/context, durable locators, language, checksums, and downstream provenance; `/search/evidence` returns that evidence ledger for Hermes instead of asking an agent to cite free-form summaries.
- Heavy graph code stays lazy-loaded. The base client target is at or below 150 KB gzip excluding lazy graph/vendor chunks.

## Hermes and reading companions

Lite Visual creates one atomic Arabic HTML+PDF pair for normal sources and one pair per book chapter. The semantic HTML article is the single canonical reading body and the A4 PDF is printed from that exact file. One source router acquires the body: a hash-verified cache, Mozilla Readability plus bounded Playwright fallback, YouTube API/yt-dlp/Whisper chain, PyMuPDF plus Tesseract OCR, EPUB spine extraction, Pandoc, or direct UTF-8. Its `lite-visual-source-extraction/v1` receipt must be complete before gapless coverage begins. After reading Intent and Frontend Design, Hermes designs every artifact fresh from its source; templates, style locks, reusable palettes, preset themes/layouts, mind maps, raster/generated images, external image agents, scripts, widgets, and mandatory pauses are forbidden. Prose carries argument and nuance; native structures and rare source-grounded inline SVG are the only code-native aids. Exact checkpoint evidence, deterministic RTL/accessibility/responsive/200%-text/A4/all-page/parity checks, a hash-bound receipt, atomic pair publication, resumable recovery, and canonical source-record verification are mandatory. Raw sources remain separate, hard technical material defaults to beginner teaching unless competence is explicit, and Notes Extractor never starts automatically.

Hermes remains the procedural Learning Compass operating system. Agent control protocol v2 (`2026-08-24`) exposes one structured capability registry that drives filtered discovery and OpenAPI, bounded Queue/profile/health context, and only two generic tools (`list_capabilities`, `site_request`). Recommendation target gaps come from `/compass/context`; direct lesson progress comes from the Thread path. The Home cockpit and `GET /agent/briefing` share one deterministic next-action projection; `GET /agent/activity` exposes verified receipts, jobs, and pending proposals. Settings → System also presents one operational-health ledger for jobs, recall load, context health, calibration, and rollout readiness. Stranded consolidation runs reconcile only from verified canonical outputs or a newly linked idempotent extraction job. Agent mutations use atomic request-fingerprinted idempotency reservations; high-risk changes require confirmation plus an exact-target field/value precondition; declared single or batch readbacks produce canonical before/after receipts, and post-commit verification failure is reported without pretending the write failed. Ordinary capture persists a validated branch atomically; deliberate remapping uses the direct canonical route and dossier readback. The NotebookLM learning router defaults to one hard source-grounded quiz, selects other media only when the concept fits, limits a plan to three outputs, and records indexed/pending/ready/failed provider truth without changing lesson completion. The existing dependency-free MCP bridge consumes these read models and the evidence search surface while preserving idempotency, risk gates, and verification. Its active workflow owns recommendation research, source-grounded candidate submission, feedback handling, typed profile learning, memory provenance, NotebookLM, code-only Lite Visual, RSS feeds, site operations, and self-evolution. It uses idempotent leases and recovery receipts but has no scheduled autonomous poller. Internal prompt payloads, job controls, and secrets do not render in normal product surfaces.

Capture interoperability includes a least-privilege Manifest V3 browser extension that opens the normal global capture dialog with a page URL or selected passage; it never stores API credentials and every capture becomes a `captured` Library record. Private deployments can enable `REQUIRE_API_AUTH=true` so reads and writes require `x-api-token`; Telegram intake is separately protected by its webhook secret, optional allowed chat ID, and durable `update_id` deduplication. Recovery is explicit and portable: checksummed D1 exports are generated by `scripts/export-recovery.mjs`, verified by `scripts/verify-recovery.mjs`, and R2 binaries must be copied and checked separately as documented in `docs/recovery.md`.
