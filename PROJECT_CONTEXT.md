# Learning Compass — Project Context

## Native Hermes tools

Repository work defaults to fast, scoped verification: affected tests, one lint/typecheck/build gate for application releases, and live readiness/smoke checks. Full suites apply to high-risk changes or explicit requests; full backup/restore applies to migrations or risky data/storage changes. Documentation-only work needs no application deployment, and unchanged checks or CI waits are not repeated by default. `docs/release-checklist.md` and Worker Ops own the detailed procedure.

Routine Thread, progress, resume, and Queue reads use the site operator's common-read table. Thread overviews stop at the hub; exact Thread/Level details are loaded only when requested. Conversational follow-ups retain observed IDs and displayed order, and user corrections replace the selected target. Read-only opening does not authorize writes. The router and operator load write-specific safeguards on demand; the manager evaluation slate covers these short requests and follow-ups against an isolated Worker fixture.

Level status/primary-source work uses the paginated metadata-only path before hydration, retaining the 1 MiB client cap. Native Compass reads, capabilities, and guarded mutations share the first-party client ledger. Ambiguous Lite Visual uploads reconcile exact canonical pair/receipt hashes without automatically repeating the POST; unresolved readback remains explicit. Operational evidence retains exact identities while user-facing replies remain natural.

The default-profile `compass-native` plugin wraps the first-party site client, canonical source extractor, PDF evidence extraction, and NotebookLM CLI. Exa is an optional discovery tool; existing default search remains unchanged. This supersedes older statements that Compass has no local model-tool schema. Worker endpoints, mutation guards, canonical storage, and specialist ownership are unchanged. No MCP service or separate Compass profile is added. Details and verification are in `integrations/hermes-compass/README.md`.

## Purpose

Hermes keeps exact verification evidence in its existing structured specialist receipt or handoff and explains the result to Mahmood in natural prose. Internal IDs remain available for inspection; successful mutation/readback, branch ownership, partial-state honesty, and permission boundaries are unchanged. Skill entry points route to task-specific references, and the instruction audit rejects missing commands/paths, frozen migration status, and mandatory reply templates.

Learning Compass is Mahmood’s private, single-user learning operating system. It turns scattered sources into a disciplined loop:

**define a Learning Thread → capture/curate sources → consume at the original source or a verified canonical companion → reflect → optionally consolidate notes/recall → complete lessons directly → resurface**

The product interface is English-first. Notes Extractor source notes optimize for durable four-year retrieval: precise English source claims and evidence are paired with concise natural Egyptian-Arabic explanation in separate directional blocks. When supported, notes include Misconception vs. Truth and complete Case Studies & Experiments coverage with researchers, year, method, findings, and source-stated limitations. Handwriting remains verbatim in native note blocks without Obsidian syntax; user-authored blocks retain their original register and direction. The product uses the `Africa/Cairo` timezone.

## Product model

- **Companion removal** retires a complete standalone HTML/PDF pair from current study materials through an explicit pair-level API. Exact source and artifact identities are checked together, and both metadata records change atomically. Immutable files remain in recovery history; source membership and lesson progress are unaffected. Corpus-managed pairs retain their separate all-target lifecycle.

- **Personal Assistant** is the natural-language intake layer for consumption history and taste discovery. In Personal Data Studio, the user can describe watched films, read books, finished series, disliked items, or current interests in ordinary Egyptian Arabic or English. `POST /assistant/interpret` returns only a reviewable preview: typed personal items, high-confidence profile signals, and no more than two follow-up questions. The model never writes by itself; explicit user confirmation plus a verified branch is required before the existing personal-library and profile-assertion writes run. This assistant is advisory and does not create Queue items, lessons, recall cards, or recommendations automatically.

- **Hardcover sync/import** is an explicit external-library bridge in Settings → Data & recovery. `POST /hardcover/sync` uses the server-only Worker secret to refresh a D1 mirror of the authenticated Hardcover account; `GET /hardcover` exposes truthful status, progress, covers, journal counts, and import linkage. Library → Books also composes that D1 mirror as read-only history: unique title/primary-author matches display once with Hardcover's state, and unmatched titles open Hardcover directly without creating an internal record, branch, dossier, chapter control, or Queue item. `POST /hardcover/import` remains the only path that imports selected or unlinked books into the typed personal ledger; it requires a verified non-pruned branch and preserves Hardcover provenance. The token is never returned to the client, and the operator must not guess a branch.

- **Learning Threads** are purpose-first objects for one question, decision, build, or capability. Complete lessons directly; each completion starts the next unfinished lesson, and the final lesson in a Level automatically activates the next Level and its first lesson. There is no separate learner-facing Level-start gate. The Thread completes when every Level's lessons are complete. A learner-confirmed correction can reopen a completed lesson, which restores its Level and Thread to active progression. Projects, sources, notes, ratings, and recall are optional context and never gate or advance progression. Notes, files, recall cards, and drafts preserve exact Thread, Level, or Lesson ownership. Thread Resources is a real material organizer: it searches the existing branch-owned Library first, attaches a source to an exact Level or Lesson, preserves visible role/contribution/order, and supports explicit edit, reorder, and removal without duplicating the canonical source. **Find material** exists only as an explicit user action for an incomplete current-Level lesson with no authored content or attached source. Its durable `compass_lesson_material` job may return one reviewable exact-lesson Compass pick or an evidence-backed abstention; the pick is isolated from ordinary Compass start/feedback state and neither outcome attaches, enters Queue, starts a session, or changes progression. Lesson sources visibly expose their persisted branch and advisory source-health state. Large course paths batch source-related D1 lookups. Agents can use the paginated `path?view=lessons&stage_id=...` projection to read one Level’s current lesson statuses and primary source IDs without hydrating bodies or artifact receipts; the full path remains compatible.
- **Books** is the first Library workspace, organized around one explicitly pinned Current Book. The dominant reading desk shows that book’s author, verified branch, Canon and Thread context, progress, one next chapter, available passive HTML/PDF/NotebookLM formats, manual completion, and an accessible chapter disclosure. Below it, My Books is an always-visible, searchable and state-filterable union of the editable branch-verified ledger and the read-only Hardcover mirror; matching identities render once, while mirror-only rows open Hardcover and expose no internal actions. The bounded first page expands incrementally instead of dumping every saved row. Canon is a visible first-class discovery section with its own search, family filters, and field visualizations that preserve the Foundation, Representative, and Boundary roles. There is no Shelf/Canon tab split, original-book action in the primary flow, or automatic fallback when the current book is cleared, finished, deleted, or tombstoned. One canonical side-effect-free server projection gives editable list and focused Book overview identical `is_primary`, personal `saved|reading|finished` state, ordered chapters, normalized companion QA, progress, next chapter, Canon memberships, and connected Threads while omitting synthetic Chapter 0; it also carries the separate side-effect-free Hardcover mirror for client composition. Canon remains an evergreen relationship model rather than a Thread or second collection. Explicit branch-preserving capture retains one book identity across personal state and Canon membership. Personal book state is independent from Queue commitment; books and chapters never appear in Queue, and Queue alone owns tracked Start/Resume actions.
- **Personal library data** records what Mahmood reads, watches, listens to, studies, or plays without pretending each item is an active learning commitment. One canonical recommendation identity can carry a typed `book|movie|series|podcast|course|game|album|other` record with explicit `planned|in_progress|completed|paused|dropped` state, optional release year/duration/progress/rating/tags/note, a verified branch, and append-only edit lineage. Books share this identity with Library → Books; personal status and progress remain separate from recommendation lifecycle and Queue. Direct ratings are preference evidence, while merely logging or completing media never advances lessons, starts a session, or requests a recommendation.
- **Sources** are reusable inputs. Lesson `primary`, `case`, `challenge`, and `reference` roles are replacement-safe single slots; `optional` is additive so several distinct extensions may coexist. Source anchors preserve an exact quote, context window, typed web/PDF/video/EPUB/artifact/text locator, language, checksum, canonical source, branch, and optional Thread. They can be resolved from a shared URL, edited, archived without deleting history, and retrieved through ordinary Search or `/search/evidence`. Saving an anchor never creates a note, Learning Unit, or recall card; each downstream object requires a separate explicit learner action and retains the exact anchor as provenance. **Learning Units** are atomic claims, concepts, methods, examples, questions, applications, and counterclaims with exact anchors, user synthesis, stance, confidence, and explained typed relations. Meaningful backlinks, cross-branch bridges, and contradiction review derive from those anchored relations, never keyword overlap. Notes are readable projections; Atlas is the navigation taxonomy.
- **Learning progression** is separate from enjoyment and utility. `retain`, `apply`, `reference`, and `drop` are source dispositions; only direct lesson completion advances a Level or Thread.
- **Recall** uses learner-authored, revisioned FSRS cards. Automated flash-card and recall-draft generation is disabled, including during retain/apply extraction. New cards require an explicit learner-authored Arabic question and answer, and failed reviews never advance progression. Recall → Needs repair shows cards after three unacknowledged lapses and any learner-paused cards with their source/anchor, review history, repair history, and nearby comparisons. A wording repair increments the content revision while preserving FSRS state; a semantic repair resets scheduling while preserving review history. Manual split creates one new learner-authored card at a time and leaves the original unchanged until the learner separately pauses or retires it. Pause, retire, restore, and explicit confirmed schedule reset are reversible, audited actions and never alter lesson state.
- **Consolidation** is explicit and durable, with visible terminal states such as closed, repair required, or waived. Hermes processes the exact work during the active workflow; no learning-core poller or autonomous recommendation chain exists.
- **Progressive note distillation** is explicit and additive. Checksum-bound claims and append-only user synthesis revisions sit above unchanged canonical note sections; explicit promotion creates a note-owned anchored Unit. Changed text marks a claim stale rather than relocating it.
- **Resurfacing** is a passive daily source-review loop with explicit star, reviewed, snooze, and dismiss controls. Frequency decay and seven-day suppression affect only resurfacing order. Frontier states, semantic links, note distillation, and resurfacing never gate or advance lessons.
- **Source health** is a persisted advisory ledger, not a crawler or automatic rewriting system. Checks classify an Original URL as `verified`, `restricted`, `unavailable`, `unknown`, or `invalid`; authentication blocks, bot challenges, throttling, server errors, and network failure remain restricted/unknown rather than being mislabeled dead. A current verdict is exposed only while its checked URL matches the normalized canonical URL, and Library → Queue can filter by that current status. Scheduled maintenance refreshes only stale Queue sources, the active lesson, and the Current Book, including any source whose persisted verdict belongs to an older URL. A replacement URL must pass a separate public-boundary verification and then a second explicit replace action bound to the same observed current URL; personal-data edits and ISBN book upserts cannot rewrite it. The old URL, verification attempt, dedup identity, and replacement lineage remain preserved. A verified coherent companion may be offered as a fallback, while a false-positive health warning never changes the canonical URL.

## Capture and recommendation rules

Saved sources and books have dedicated item pages with addressable Overview, Files, Notes & passages, Recall, Connections, History, and Reflection sections; books retain Chapters. The same source identity is used across Home, Library, Search, personal history, and learning material. Opening titles is passive, and explicit content controls remain separate. Notes/cards/Units link to their owning source's files and notes. Artifact details load an exact metadata record, including scoped or older files, with the same hidden-publication/deleted-source boundary as content access. Section changes preserve mounted editor state; reload preserves the selected section, not an unsaved draft.

- Every URL, text, PDF, HTML, video, Telegram, share-target, RSS, and Atom capture becomes a durable `captured` source record. A share-target POST first persists an opaque pending intake before redirect. A URL plus distinct prose remains a durable unresolved review until the learner explicitly chooses whole-source capture or selected-passage anchor; the same choice is idempotent and a conflicting stale choice is rejected. Ordinary shares become canonical source records only after reviewed branch selection succeeds, while selected-passage intakes close only after their exact active annotation matches the canonical source branch in the same guarded write. An unfinished intake remains recoverable after the app closes and is never treated as a branchless source. Manual capture and each RSS/Atom subscription require a reviewed non-pruned branch; newly created feed source records inherit that default atomically with mapping provenance, while a deduplicated source preserves its existing reviewed mapping and exposes the conflict in the import receipt. Queue remains the explicit commitment step; enabled feeds refresh every six hours, scheduled imports are capped at 20 deduplicated entries per feed, and manual Check now is capped at five latest entries per feed.
- Global **Add anything** also accepts personal books, movies, series, podcasts, courses, games, albums, and other media. These writes require a verified non-pruned branch, deduplicate canonical URLs or stable type/title/creator identity, remain editable in Settings → Data & recovery, and never enter Queue automatically. A source capture and a personal-media record are distinct intents even though both reuse canonical recommendation identity, ratings, branches, exports, and recovery.
- Queue normally holds five queued/in-progress sources. Explicit triage override is required to exceed the cap. Queue owns start, resume, return, and completion; opening a source, file, or companion elsewhere is passive and never creates a session. Every Queue item carries its branch context (`branch` id/label/status), note presence, recall count/due, and companion artifact links.
- Branches are the primary organizing axis. `tree_nodes` is the branch store; `recommendation_meta.branch_id` is the canonical source-to-branch linkage (dedup-key prefix resolution is the legacy fallback). The taxonomy follows a clean 3-tier domain structure: Super Category (Domain) → Knowledge Branch (`tree_nodes`) → Topics/Leaves (`meta_json.leaves`), with explicit priority rank (1–5) and status (`love`, `active`, `held`, `pruned`). Synthetic round numbering (R1/R2/R3) has been retired. Map → Review → Branches allows creating and editing branch scope, priorities, status, and boundaries. The branch manager, linked-items ledger (`/brain/branches/:id/items`), and unified source dossier present the same canonical branch identity.
- Feedback is explicit, structured, and auditable. The source dossier separates finished, continue-later, and stopped states; stopped feedback requires a reason and atomically exits Queue as rejected/excluded, while not now remains neutral and in-progress feedback preserves the commitment. Rating, disposition, completion, expectation-versus-result, effort, and later recall/application outcomes remain separate. Compass and ordinary feedback share one metadata contract, Taste Mapper receives the complete event history, and every write returns an analysis/note receipt. Processing feedback never requests another recommendation automatically.
- Compass is Thread-first and source-grounded. It exposes current missing-material lessons as exact recommendation targets, verifies every candidate and claim URL through a public-only redirect-safe boundary, and attaches a started targeted pick to that lesson without changing lesson progress. Fit, bridge, and challenge lanes remain bounded by source evidence and rollout gates; decision confidence is explicitly heuristic until a true outcome calibration exists. Mastered/consumed sources and Mahmood’s standing exclusions are always applied.
- Adaptive depth uses direct lesson completion and explicit depth feedback only as advisory ranking signals. Perspective labels require candidate evidence indexes, and explicit delivery context may describe device, time, energy, language, or reading mode; unknown values stay neutral and Queue order remains canonical.
- User-authored reflection is never rewritten. Invisible AI may enrich, rank, classify, and explain. Typed profile changes have provenance, confidence, version history, and reversible undo; Hermes self-evolution is evidence-gated, explicit, and unscheduled.
